# ADR-001：Relay、Daemon 与当前传输边界

- 状态：Accepted，2026-08-16 按当前实现修订；Daemon 命令流细节由 ADR-009 补充
- 日期：2026-08-13

## 背景

系统需要把多个 PC 本地工作区安全地暴露给 Android 和 Web，同时支持断线恢复、事件流和异步控制。服务器不能访问工作区，也不能读取端到端加密正文。

## 决策

采用三层边界：

1. Relay Server 只负责认证、路由、密文持久化、事件重放、presence、租约和命令状态。
2. PC Daemon 是唯一访问工作区和 Provider 进程的组件。
3. Android/Web/Admin 是客户端；Android 是唯一写控制端，Web/Admin 只读。

当前已经实现的传输职责如下：

- REST：认证、配对、快照、历史分页、附件和异步命令提交。
- SSE：账号级可恢复增量读取，支持 `Last-Event-ID`。

当前 Relay 没有 WebSocket 路由，也没有 Daemon 的认证命令流、心跳、ack 或事件回写端点。`apps/daemon` 的 `run` 仍是本地 mock 心跳，`runner` 只消费本地 SQLite outbox；它们不得被表述为已连接 Relay。

后续 Daemon 下行命令流采用 REST + 专用 SSE 的方案，命令确认、事件上传和版本协商由 ADR-009 定义。WebSocket 不是当前实现，也不是本轮默认传输；如未来确有性能或双工需求，必须以独立 ADR、负载数据和兼容策略重新决策。

采用 SQLite 作为权威存储，进程内内存只保存可重建的 presence、短租约和广播状态；事件写入使用 transactional outbox。单租户自托管不引入 PostgreSQL/Redis 运行时依赖。

## 取舍

- REST/SSE 更容易实现快照、分页、游标恢复和代理环境下的调试。
- 相比 gRPC，JSON 协议更适合 Flutter、Vue 和跨平台调试。
- 内存 presence 不保存业务真相，进程重启只会短暂丢失在线状态，不会丢会话历史。

## 后果

现有 REST/SSE 契约必须持续测试。P2 新增命令流前，必须先把版本、游标、幂等键、异步命令状态和撤销语义写入 OpenAPI/JSON Schema；WebSocket 用例在当前版本保持 `excluded`，不能用来声称已覆盖。
