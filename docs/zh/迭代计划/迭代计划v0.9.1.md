# Agent Sessions 迭代计划 v0.9.1：Terminal Presence 与无感在线态收敛

> 状态：`planned`（2026-09-08；本轮只完成诊断、契约冻结、实施计划和结构化测试用例，不修改运行代码。）
>
> 前序：[迭代计划 v0.9.0](迭代计划v0.9.0.md)（已交付）；权威当前事实以[项目文档](../项目文档.md)为准；长期测试 ID 登记于[测试套件索引](../../test/测试套件索引.json)。

本期聚焦一个用户问题：Daemon 明明持续向 Relay 发送 heartbeat，移动端却因为缓存未刷新或客户端墙钟判断而显示“终端离线”，并且卡片标题仍硬编码为“在线”。目标是把 Terminal Presence 变成 Relay 权威、可过期、可恢复的事实，并让前台 App 自动更新且不打扰用户。

## 0. 复核结论与版本边界

当前“持续心跳检测”实际混用了三种机制：

1. **Terminal presence heartbeat**：Daemon 每 15 秒向 Relay 的 hello/heartbeat，证明执行端仍然存活。
2. **SSE keepalive heartbeat**：事件流连接中的注释或保活帧，只证明连接仍可读，不能证明 Terminal 进程仍存活。
3. **Flutter terminal list refresh**：移动端刷新 `/v1/terminals` 的动作，目前只在首页首次打开时发生，不能承担持续 presence 检测。

v0.9.1 冻结以下总原则：Relay 以服务端时间、最后一次有效 heartbeat 和 heartbeat interval 计算 Terminal Presence；客户端不得用自己的墙钟重新裁决“能否投递命令”。`/v1/terminals`、Workspace/DSH 命令选择和移动端状态展示必须消费同一个 availability 语义。Flutter 以前台生命周期为边界自动同步，刷新对用户不可见，不闪 loading、不清空旧列表、不弹刷新提示。

本期不重新纳入会话级 SSE、后台常驻、系统推送或 WebSocket。v0.9.0 已交付的账号级 SSE 和会话事件流保持既有语义，仅做兼容回归。

## 1. 已复现故障链

### 1.1 用户可见问题

诊断附件中的页面出现同一张矛盾卡片：标题为 `darwin · 在线`，正文却为 `终端离线，无法请求同步。`。这会让用户误以为需要手工重启或重新配对。

### 1.2 根因证据

| 层 | 当前行为 | 影响 |
| --- | --- | --- |
| Daemon | 每 15 秒向 Relay heartbeat，Relay 返回 200 | 执行端本身正常，不能解释 UI 离线 |
| Relay | hello/heartbeat 把数据库 `terminals.status` 写为 `online`；列表接口直接返回持久化 status | Daemon 崩溃后可能长期保留 online |
| Relay | Workspace/DSH 选择主要检查 `status == online` 和 capability，不检查 heartbeat freshness | 失联目标可能继续进入投递链路 |
| Flutter | `TerminalSummary.availabilityAt()` 用客户端当前时间与缓存 `lastSeen` 二次判 stale，阈值约 90 秒 | 页面缓存超过阈值后显示离线，即使 Relay 事实已恢复 |
| Flutter | `TerminalStatusController` 只有手动 `refresh()`；首页只在 `initState` 刷新一次 | 前台停留期间不会自动获取新状态 |
| Flutter UI | `_terminalGroups()` 使用 availability，但 `_TerminalWorkspaceCard` 只要 terminal 非空就硬编码“在线” | 标题、正文、按钮门控来自不同事实源 |
| 测试 | 没有持续刷新、deadline 投影、命令门控的跨层回归 | 事故可发生而 full gate 仍可能通过 |

### 1.3 已排除范围

- Relay/Daemon 的基本 heartbeat HTTP 链路不是本次主故障；保留既有 hello/heartbeat 与 v0.8.9 生命周期回归。
- 不修改 canonical session event envelope、Provider、真实模型调用或加密协议。
- 不要求移动端后台持续联网；后台停止新请求，回到前台再恢复。
- 不做破坏性数据库迁移；保留既有 `last_seen`，采用 additive 字段或运行时投影。

## 2. 目标与验收标准

- **G1 Relay 权威 Presence**：Relay 基于 heartbeat deadline 即时投影 `online/offline/unknown`，不依赖后台 sweeper 才正确。
- **G2 命令安全门控**：Workspace/DSH 写命令使用与列表相同的 predicate；过期目标返回稳定 `TERMINAL_OFFLINE`，不创建投递。
- **G3 自动失效通知**：heartbeat 恢复、过期和重新上线触发轻量 presence invalidation；通知丢失时有安全对账兜底。
- **G4 Flutter 无感同步**：认证有效、前台、网络可用时自动刷新；后台、离线、注销、换账号和 dispose 后零新请求且不接受迟到响应。
- **G5 单一 UI 状态源**：卡片标题、正文、按钮可用性和终端状态页全部来自同一 availability 投影。
- **G6 restart 可诊断**：`restart.sh` 以“首个 heartbeat confirmed”作为启动门，并提供脱敏 freshness 诊断。

必须观察到：持续 heartbeat 时，App 前台停留超过旧 90 秒阈值也不误报离线；停止 heartbeat 后 Relay 在 deadline 内权威投影 offline；恢复 heartbeat 后 App 自动回 online；Relay 不可达时显示 `unknown/unreachable`，不把网络故障说成执行端离线；生命周期边界没有请求泄漏或迟到污染。

## 3. 影响面与冻结契约

### 3.1 影响模块

- Relay/Daemon：`internal/domain/daemon.go`、`internal/store/sqlite.go`、`internal/httpapi/handlers.go`、`internal/domain/workspace.go` 及 Terminal 写命令选择路径。
- Flutter：`apps/mobile/lib/domain/terminal_models.dart`、`terminal_status_controller.dart`、`runtime_recovery_binding.dart`、`lifecycle_recovery_controller.dart`、`providers.dart` 和 `session_screens.dart`。
- 测试：Relay/domain/httpapi 集成测试、Flutter 状态机/widget 测试、`tools/restart_test.sh`、`e2e-verify/mobile` headed fixture。

### 3.2 C1 Presence 输入与阈值

- `last_heartbeat_unix_ms` 是唯一活性输入；hello 与 heartbeat 幂等刷新它，并产生单调 `presence_revision`。
- 默认参数冻结为 heartbeat `15s`、suspect/unknown 观察窗口 `40s`、offline deadline `60s`。阈值集中配置并可注入测试。
- Relay 使用服务端时间口径计算有效期；客户端墙钟只用于展示，不决定授权或写命令。
- `online`、`offline`、`unknown`、`unsupported` 必须分开；`unknown` 表示事实不可确认，不等于执行端离线。
- `/v1/terminals` additive 返回 `availability`、`presence_revision`、`last_heartbeat_unix_ms` 和可选 `next_check_unix_ms`。read path 和 command path 都即时派生过期状态，reaper 只负责通知或持久投影。

### 3.3 C2 命令 predicate

Workspace 创建、DSH 同步和后续 Terminal 写命令只能选择 `availability == online` 且 capability 满足的目标。stale/offline/unknown 不得新建可投递 command，返回稳定 `TERMINAL_OFFLINE` 或 `TERMINAL_UNREACHABLE`。列表显示 online 后到提交之间再次过期时，以 Relay 提交时判断为准。

### 3.4 C3 通知与客户端同步

- 优先复用账号级 `/v1/events` 发布轻量 `terminal.presence.changed`；事件只做失效通知，App 收到后重新拉 `/v1/terminals`，不直接携带完整 DTO。
- heartbeat/hello 负责 online/recovery 变化；presence reaper 负责过期变化。通知按 revision 单调去重。
- Flutter 由专门 controller/state machine 管理，前台保留 `45-60s` 带 jitter 的 safety reconcile。手动刷新、通知、定时对账和生命周期恢复共用 single-flight/pending coalescing。
- 认证/设备变化、注销、dispose 递增 auth generation；页面切换递增 selection generation；迟到 Future 不得 notify 或污染新账号/页面。
- 后台/offline 停止新请求；恢复只触发一个去重首拍。quiet refresh 保留最后可信列表，不闪 loading，不把失败改写成 offline。

### 3.5 C4 UI 与 restart

卡片标题、正文、同步按钮门控、禁用原因和状态页必须消费同一 `TerminalAvailability`；禁止只要 `terminal != null` 就显示“在线”。状态变化不得清空卡片或造成布局跳动，稳定 Key/Semantics 必须保留。

`restart.sh` 只有在 Relay 可达、配对/注册完成且首个 heartbeat confirmed 后才报告 Daemon ready；只进程存活不算 ready。status/diagnostics 只输出进程存活、heartbeat age bucket、presence result、重连次数和失败分类，不输出 token、Terminal ID、路径、正文或密钥。保留 poll-only 开关作为通知路径回滚。

## 6. 验证口径、回滚与完成定义

本轮是 planning，不运行功能 full gate，不声称 v0.9.1 已实现或通过。计划阶段仅验证文档和 JSON：`real_browser=false`、`real_model=false`、`real_upstream=false`、`fixture_data=true`、`local_test=true`、`headless=false`。实现阶段预留 `task test:v091:local` 为唯一 local gate；可见验收为 `real_visible_flutter=true`、`headless=false` 的 macOS Flutter fixture，不扩大为真实浏览器、真实模型或真实上游结论。

主要风险与回滚：Relay 仍是命令事实源，客户端保留 poll-only；invalidation 只做加速，read/command deadline 不依赖 reaper；single-flight、jitter 和 generation 防止请求风暴与迟到污染；网络失败使用最后可信状态加 unknown；不回滚数据库字段或既有 session event schema。

v0.9.1 只有在 V091-01..14、v0.8.9/v0.9.0 相关回归、唯一 full gate、headed 可见验收和覆盖审计全部通过后才能标记 `delivered`。未运行的真实浏览器、真实模型、真实上游和 Android 实机必须保持 false。
