# Agent Sessions 迭代计划 v0.6：Go 后端技术栈优化（Gin + Redis + Kafka + GORM）

> 状态：`planned`
> 本文仅制定迭代计划，不实施任何代码或迁移改动。实施前需按本计划完成决策门、ADR 更新和测试基线确认。
> 编写参考：`web-iterative-workflow` SKILL.md；事实来源为仓库内 `README.md`、`docs/zh/项目文档.md`、`docs/zh/技术选型.md`、`docs/adr/`、`Taskfile.yml`、`deploy/docker-compose.yml`、`internal/store` 与 `internal/domain` 现有实现。
> 联网说明：已通过 Go module proxy（goproxy.cn）确认关键依赖版本与 Go 版本兼容性；当前环境未访问通用搜索引擎/社区文章，因此“事务性 outbox 最佳实践、Docker Compose 生产配置”等仍标记为实施前按官方文档验证。

## 1. 目标

把当前 Go 后端技术栈从“Gin + SQLite 手写 SQL + 进程内 Presence/Outbox”优化为：

- **Gin**：继续作为 HTTP/SSE transport 层，不发生框架替换。
- **GORM**：作为数据访问层，替换/收敛 `internal/store/sqlite.go` 中大量手写 SQL 仓储实现，同时保持 `store.Repository` 领域端口不变。
- **Redis**：作为可重建状态与短时效基础设施，用于在线 presence、限流、幂等键缓存、分布式租约辅助、SSE 多实例 fanout。
- **Kafka**：作为事务性 outbox 的异步事件总线，用于已提交事件/命令变更的可靠投递、投影/通知/用量/审计等消费端解耦。

本迭代不改变产品功能、公开 API、OpenAPI/JSON Schema、E2EE 边界、Android 唯一写控制权或“SQLite/数据库是权威存储”的原则；Redis 和 Kafka 均不作为业务真相的唯一来源。

## 2. 背景与现状

### 2.1 当前实现

- Relay 使用 `github.com/gin-gonic/gin`，数据库使用 `modernc.org/sqlite` + 手写 SQL + `internal/store/migrate.go` 编号迁移。
- `internal/store/repository.go` 定义了庞大的 `Repository` 端口，`internal/store/sqlite.go` 是手写 SQL 实现。
- presence、SSE 订阅和广播使用 `internal/domain/presence.go` 的进程内 `PresenceHub`；重启后由 SQLite 恢复。
- outbox 已有 `outbox` 表和 `OutboxWorker.Drain`，但目前“投递逻辑”只是标记 done，没有真实异步投递目标。
- 当前架构文档和 ADR 明确“不引入 Redis/Kafka/GORM”：`docs/zh/技术选型.md` 第 5/9 节、`docs/adr/ADR-006-技术栈与语言边界.md`、`docs/adr/ADR-008-SQLite权威存储.md`、`docs/adr/ADR-001-传输与组件边界.md`。
- `deploy/docker-compose.yml` 只启动 Relay + SQLite，不依赖外部中间件。

### 2.2 为什么需要 v0.6

- 当前进程内 `PresenceHub` 只支持单实例，无法安全扩展到多 Relay 实例。
- 当前 `OutboxWorker` 是空转实现，异步事件没有真实投递、重试、死信和消费端解耦。
- 手写 SQL 仓储方法多、样板多，GORM 可以降低新增表和查询的维护成本，但必须保留事务、错误映射和迁移控制。
- Redis/Kafka 可为后续水平扩展、事件驱动投影和可观测性打基础。

### 2.3 现状冲突与决策门

引入 Redis/Kafka/GORM 会推翻 ADR-006 / ADR-008 / `技术选型.md` 中的明确不引入项。因此 v0.6 的第一步不是写代码，而是：

1. 新增 ADR（建议 `ADR-012-Go后端中间件与异步事件总线`），明确 Redis/Kafka 的职责边界、不是权威存储、以及多实例扩展目标。
2. 修订 `ADR-006` 中“不使用 GORM/Kafka/Redis”的描述，改为“GORM 作为存储适配器；Redis/Kafka 作为可重建状态与事件总线，不保存业务真相”。
3. 修订 `ADR-008` 与 `ADR-001`，补充“SQLite 仍为权威存储；Redis/Kafka 不替代数据库，只在能力需要时引入”。
4. 同步更新 `docs/zh/技术选型.md`、`docs/zh/项目文档.md`、`deploy/docker-compose.yml` 与 `.env.example`。

## 3. 目标架构

```text
Gin HTTP/SSE
   │
   ├─► domain / application（不变，*gin.Context 不进入领域层）
   │        │
   │        ▼
   │   store.Repository 端口
   │        ├─► GORM Repository 适配器 ──► SQLite（权威存储，仍走编号迁移）
   │        └─► 旧 sqliteRepo（过渡期双实现，feature flag 切换）
   │
   ├─► Redis
   │     ├─ presence / last-seen（可重建，不存业务真相）
   │     ├─ rate limit / idempotency cache（TTL）
   │     ├─ distributed lock / lease hint
   │     └─ pub/sub：多实例 SSE 本地 Hub 之间的 fanout 提示
   │
   └─► Kafka 事件总线
         ├─ 事务内写 SQLite outbox
         ├─ Outbox Publisher：把 outbox 投递到 Kafka topic
         ├─ Consumer：账号事件投影 / 通知 / 用量聚合 / 审计 / 清理任务
         └─ DLQ / 重试 / 幂等消费
```

关键约束：

- **GORM 不进入 domain/handler**：只在 `internal/store/gorm` 适配器内使用 `*gorm.DB`；`store.Repository` 保持现有签名，错误映射到现有 `sql.ErrNoRows` / `store.ErrNotFound` 语义。
- **Redis 不保存业务真相**：在线状态、限流计数、幂等缓存、租约 hint 可丢失；丢失后由 SQLite/DB 和客户端 heartbeat 重建。
- **Kafka 不做命令投递替代**：Daemon 命令流继续使用 ADR-009 的 REST + 专用 SSE；Kafka 只承载已提交事件/命令变更的异步总线，不改变命令投递与 ack/result 事实源。
- **数据库默认仍为 SQLite**：v0.6 不把 SQLite 替换为 PostgreSQL/MySQL。若后续性能/多实例要求必须换库，需另开 ADR。

## 4. 范围边界

### 4.1 纳入

- GORM 依赖与 `internal/store/gorm` 适配器，覆盖 `store.Repository` 全部或分阶段大部分方法。
- Redis 客户端与适配器：`PresenceStore`、`RateLimiter`、`IdempotencyCache`、`DistributedLock`、`EventFanout`。
- Kafka 客户端与适配器：`OutboxPublisher`、`EventConsumer`、`DLQ`、`ConsumerGroup`。
- 配置：新增 Redis/Kafka/GORM 环境变量、feature flag、本地默认值、`.env.example`。
- 部署：更新 `deploy/docker-compose.yml` 增加 redis/kafka（开发/测试环境），更新 `restart.sh` 或 Taskfile 的启动/健康检查/清理流程。
- 测试：单元、集成、契约测试；测试容器或本地二进制启动 Redis/Kafka；新增稳定测试 ID。
- 文档：ADR、技术选型、项目文档、自动化测试文档、实施计划、迭代计划。
- 迁移：outbox 表新增投递所需列；GORM 模型与现有 SQL migration 的一致性校验。

### 4.2 不纳入

- 不修改公开 REST/SSE 路径、请求/响应字段、错误码或协议版本。
- 不改变 Android、Web、Admin 客户端行为。
- 不把 SQLite 权威存储替换为 PostgreSQL/MySQL。
- 不把 Daemon 命令流从 REST+SSE 改为 Kafka。
- 不引入 WebSocket 作为新的默认传输。
- 不实施生产级多实例自动扩容、Kubernetes 或云托管。
- 不把 Redis/Kafka 作为业务数据的唯一持久层。

## 6. 分阶段实施计划

### P0：决策门、ADR 与配置基线

目标：把“引入 Redis/Kafka/GORM”从个人偏好变成有记录的架构决策，并建立可切换的配置骨架。

交付物：

1. 新增 `docs/adr/ADR-012-Go后端中间件与异步事件总线.md`，记录：
   - Redis/Kafka 不是权威存储；
   - GORM 是 store 适配器，不进入领域层；
   - 保持 SQLite 权威、REST+SSE 命令流、E2EE 边界。
2. 修订 `ADR-006`、`ADR-008`、`ADR-001` 和 `docs/zh/技术选型.md`。
3. 扩展 `internal/config`：
   - Redis URL、Kafka brokers、topic 前缀、GORM driver、feature flag；
   - 所有新增配置支持从环境变量读取，不允许把密钥写入日志。
4. 更新 `.env.example` 和 `deploy/docker-compose.yml`：
   - 增加 `redis`、`kafka` 服务（开发/测试用，默认不阻塞纯本地模式）；
   - 增加健康检查。
5. 更新 `Taskfile.yml` / `restart.sh` 的启动与清理逻辑。

验收：

- 无代码行为变化；`task check`、既有 Go 测试仍通过。
- 新增配置可通过环境变量打开/关闭。
- 文档校验通过。

### P1：GORM 存储适配器

目标：在不改变 `store.Repository` 端口的前提下，用 GORM 实现数据访问，并用 feature flag 切换。

工作内容：

1. 引入 D1 依赖，新增 `internal/store/gorm/gorm_repo.go`、`gorm_models.go`、`gorm_tx.go`。
2. 将现有 `store.Repository` 的账号/设备/Token/配对/会话/事件/命令/投递/outbox/usage/feedback 等按模块迁移。
   - 建议按领域模块分小切片迁移，每个切片跑既有对应测试。
3. 错误映射：
   - GORM `gorm.ErrRecordNotFound` 映射为 `sql.ErrNoRows` 或 `store.ErrNotFound`，保持 domain 层判断不变。
   - 唯一约束冲突映射为与当前 SQLite 驱动一致的行为。
4. 事务：
   - `WithTx` 使用 GORM `Transaction` 或 `*gorm.DB.Begin()`；
   - 保证事务内 `Repository` 方法使用同一 `*gorm.DB`。
5. 迁移一致性：
   - 为每张表建立 GORM model；
   - 新增 `internal/store/gorm/schema_test.go`，把 GORM model 映射的表结构（列、索引、外键）与 `internal/store/migrate.go` 的 SQL schema 对比，防止漂移。
6. feature flag：
   - `AGENT_SESSIONS_STORE_DRIVER=legacy|gorm`；
   - 默认保持 `legacy` 直到全量迁移完成并通过完整回归。

验收：

- 同一组集成测试在 `legacy` 和 `gorm` 两种 driver 下均通过。
- `RELAY-DB-*`、`MIG-*`、`RELAY-REDIS-01` 等现有用例在 GORM 模式下语义不变。
- 领域层未引用 GORM。

### P2：Redis 适配器

目标：为 presence、限流、幂等缓存、分布式锁与多实例 fanout 提供 Redis 实现，同时保留内存实现作为单机/测试模式。

工作内容：

1. 引入 D3 依赖，新增 `internal/infra/redis` 或 `internal/cache/redis` 包。
2. 抽象 `PresenceStore` 接口：
   - `Touch`、`Online`、`Snapshot`、`Subscribe`、`Publish`、`SubscribeAccount`、`PublishAccount`；
   - 现有 `domain.PresenceHub` 作为内存实现，新增 `RedisPresence` 实现同一接口。
3. 重构 `httpapi.API.Events` 从具体 `*domain.PresenceHub` 改为接口，避免 handler 依赖具体实现。
4. 使用 Redis 实现：
   - presence：`SET device:<id> <last_seen_ms> EX <ttl>`、`SADD account:<id>:devices`；
   - 限流：`INCR` + `EXPIRE` 或 sliding window；
   - 幂等键缓存：`SET idem:<scope>:<key> <command_id> NX EX <ttl>`；
   - 分布式锁：`SET lock:<key> <token> NX EX <ttl>` + Lua 释放；
   - SSE fanout：Redis Pub/Sub 或 Stream 作为多实例 Hub 的提示，收到提示后仍从 SQLite/DB 回放事件。
5. 配置：
   - `AGENT_SESSIONS_REDIS_ADDR`、`AGENT_SESSIONS_REDIS_PASSWORD`、`AGENT_SESSIONS_REDIS_DB`、`AGENT_SESSIONS_REDIS_TLS`；
   - `AGENT_SESSIONS_PRESENCE_DRIVER=memory|redis`；
   - 未配置 Redis 时仍可用内存实现。
6. 健康检查：
   - `/readyz` 在启用 Redis 后检查 Redis `PING`，失败时服务不可用或降级（feature flag 决定）。

验收：

- presence 在 Redis 重启/丢失后可由 SQLite/DB + heartbeat 重建，不丢业务数据。
- 多实例测试可以验证：一个 Relay 写入事件后，另一个 Relay 的本地 SSE 订阅者能通过 Redis Pub/Sub 提示后从 DB 回放拿到事件。
- `RELAY-REDIS-01` 从“进程内 presence 重启后重建”扩展为“内存或 Redis presence 丢失后均可由 SQLite/DB 重建”，测试 ID 不变或按规则新增。

### P3：Kafka 事务性 Outbox 与事件总线

目标：让现有 outbox 成为真正的可靠异步投递通道，并建立消费端。

工作内容：

1. 引入 D2 依赖，新增 `internal/events/kafka` 或 `internal/events` 包。
2. 扩展 outbox 表结构（additive migration）：
   - `topic TEXT NOT NULL DEFAULT ''`；
   - `key TEXT NOT NULL DEFAULT ''`；
   - `published_at INTEGER`；
   - `last_error TEXT`；
   - `available_at INTEGER`；
   - `trace_id TEXT`；
   - 保留 `id`、`kind`、`payload_json`、`status`、`attempts`。
3. 实现 `OutboxPublisher`：
   - 从 SQLite/DB 拉取 pending outbox；
   - 序列化为 Kafka message（只包含白名单元数据 + 密文 envelope，不包含明文正文/密钥）；
   - 使用幂等 producer（若客户端支持）或至少一次投递；
   - 成功后标记 `published_at` 和 status；失败标记 `last_error`、递增 attempts，超过阈值进入 DLQ。
4. 定义 topic 与消息 schema：
   - `agent-sessions.relay.events`：账号/会话事件变更；
   - `agent-sessions.relay.outbox.commands`：命令状态变更；
   - `agent-sessions.relay.deadletter`：死信。
   - 消息 key 建议使用 `account_id` 或 `session_id`，保证同一会话事件有序。
5. 实现至少一个消费端验证闭环：
   - `EventConsumer` 消费 `agent-sessions.relay.events`，执行投影/通知/用量/审计等；
   - 消费幂等：Redis 或 DB 中去重已处理 `event_id`/`outbox_id`；
   - 失败重试与 DLQ。
6. 保留 Daemon 命令流不变：
   - Kafka 不替代 `/v1/daemon/commands/stream`；
   - 命令投递、ack/result 仍走 ADR-009 REST+SSE。
7. 配置：
   - `AGENT_SESSIONS_KAFKA_BROKERS`、`AGENT_SESSIONS_KAFKA_TOPIC_PREFIX`、`AGENT_SESSIONS_KAFKA_GROUP_ID`、`AGENT_SESSIONS_KAFKA_ENABLED`；
   - 未启用 Kafka 时 outbox 保持当前“空转/标记 done”或仅记录日志，不影响既有功能。

验收：

- 写入业务事务后，outbox 能通过 Kafka 被消费端收到。
- 消费端重复收到同一消息不会重复更新聚合/通知。
- Kafka 故障时业务写入不受影响（outbox 留在 DB），恢复后继续投递。
- 不改变现有 REST/SSE 与 Daemon 命令流测试。

### P4：横切集成、测试与性能验证

目标：把 GORM、Redis、Kafka 放一起跑通，并补齐自动化测试。

工作内容：

1. 测试架构：
   - 单元测试：GORM repository 错误映射、Redis presence/limit/lock、Kafka outbox serialization。
   - 集成测试：使用本地 Redis/Kafka（Docker Compose 或测试容器）跑真实链路。
   - 契约测试：确认 public API 行为与旧实现一致。
   - 回归测试：既有 `task check`、`task test:relay`、`task test:daemon`、`task test:e2e:relay` 全部在默认与全中间件模式通过。
2. 新增稳定测试 ID（建议）：
   - `STACK-GORM-01`：GORM 与 legacy 仓储在相同 fixture 下结果一致。
   - `STACK-GORM-02`：GORM 事务 `WithTx` 回滚与错误映射。
   - `STACK-REDIS-01`：Redis presence 丢失后由 SQLite 重建。
   - `STACK-REDIS-02`：Redis 限流/幂等缓存 TTL 与并发安全。
   - `STACK-KAFKA-01`：事务 outbox 发布到 Kafka 并被消费端幂等消费。
   - `STACK-KAFKA-02`：Kafka 故障时业务写成功，outbox 不丢，恢复后继续投递。
   - `STACK-KAFKA-03`：未知/损坏消息进入 DLQ，不阻塞正常消费。
3. 性能验证：
   - 对比 legacy SQL vs GORM 的读写延迟、连接数和事务吞吐；
   - 对比 memory presence vs Redis presence 的延迟；
   - 验证 Kafka 生产/消费吞吐与背压。
   - 性能数据用于判断是否继续保留 feature flag 或切换默认。

验收：

- 全量既有 Go 测试通过。
- 新增 `STACK-*` 用例纳入 `docs/test/测试套件索引.json` 并保持唯一 ID。

## 9. 验收标准

1. 所有既有公开 API 路径、字段、错误码和协议版本保持不变；OpenAPI/JSON Schema 生成物无漂移。
2. `store.Repository` 端口不变；领域层不出现 `*gorm.DB`、Redis client 或 Kafka client。
3. 默认本地启动仍可不依赖 Redis/Kafka；开启后也能通过健康检查。
4. GORM 模式通过全部既有 store/domain/relay 测试；legacy 模式仍保留为回滚路径。
5. Redis presence 丢失、Kafka 故障或消费端重启不会造成业务数据丢失或重复累加。
6. Outbox 不再空转：启用 Kafka 后有真实投递、重试、DLQ 和消费幂等证据。
7. `RELAY-REDIS-01` 等历史测试按新语义更新并通过。
8. ADR-001/006/008、技术选型、项目文档、自动化测试文档、README 和 deploy 配置全部回填当前事实。
9. 完成至少一次回滚演练：从全中间件模式切回 legacy/memory/outbox-noop，数据无丢失。
10. 本轮只交付计划与文档；实施阶段另行按 P0→P5 执行。

## 10. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 与现有 ADR/技术选型冲突 | 架构方向不一致，评审阻塞 | P0 先新增/修订 ADR，明确 Redis/Kafka/GORM 边界 |
| GORM 与现有手写 SQL 行为不一致 | 数据读写回归 | 双实现 + feature flag + 全量 fixture 对比测试 |
| Redis 被误用为业务真相 | 丢失会话/命令/事件 | 文档与代码评审强制“Redis 只保存可重建状态”；关键数据只写 DB |
| Kafka 至少一次导致重复消费 | 重复通知/用量累加 | 消费幂等（event_id/outbox_id 去重）；新增 STACK-KAFKA-01 |
| Kafka 增加部署复杂度 | 本地开发门槛提高 | 默认零外部依赖；Redis/Kafka 仅在需要时开启；docker compose profile |
| 迁移期间 schema 漂移 | GORM model 与 SQL migration 不一致 | `STACK-GORM-03` 自动对比；生产禁用 AutoMigrate |
| 分布式锁/lease hint 与 SQLite 事务冲突 | fencing 失效 | lease 仍以 DB 事务为准；Redis 锁只作提示/短超时辅助 |
| 性能未达预期 | 优化收益不明显 | P4 做基准；如无收益，保留 legacy/memory 为默认并记录结论 |

## 12. 联网确认结果与仍待验证清单

### 已通过 Go module proxy（goproxy.cn）确认

1. GORM：`gorm.io/gorm v1.31.2`，go.mod 要求 `go 1.18`，与当前 Go 1.26.3 兼容。
2. GORM SQLite driver：`github.com/glebarez/sqlite v1.11.0` 为纯 Go、无 CGO，基于 modernc；不采用 `gorm.io/driver/sqlite v1.6.0`（依赖 `github.com/mattn/go-sqlite3`，需要 CGO）。
3. Kafka Go client：`github.com/segmentio/kafka-go v0.4.51`，go.mod 要求 `go 1.23`，与当前 Go 1.26.3 兼容；源码包含低层 `Conn`/`Dialer` 的 `TransactionalID`/幂等投递支持，高层 `Writer` 支持 `RequiredAcks`、重试和异步发送。
4. Redis client：`github.com/redis/go-redis/v9 v9.22.0`，go.mod 要求 `go 1.24`，与当前 Go 1.26.3 兼容；源码包含 Cluster、Sentinel、TLS、Pub/Sub 支持。

### 仍需实施时按官方文档/社区实践验证

1. Gin + GORM + Redis + Kafka 在单租户自托管场景下的 Docker Compose 生产配置、数据卷和健康检查最佳实践。
2. 事务性 outbox + Kafka 的参考实现模式：topic 分区数、key 策略、重试上限、DLQ、消费幂等。
3. Kafka broker 3.x/4.x 与 `segmentio/kafka-go v0.4.51` 的事务/幂等 producer 实际兼容性。
4. Redis 7/8 与 `go-redis/v9 v9.22.0` 的 Sentinel/Cluster/TLS 实际配置验证。
5. `glebarez/sqlite v1.11.0` 与 `gorm.io/gorm v1.31.2` 在项目既有 SQLite schema 上的完整回归验证。
6. SQLite 暂不替换；如未来需要 PostgreSQL/MySQL，应基于真实压测和部署约束另立 ADR。
