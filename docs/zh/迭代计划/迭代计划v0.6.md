# Agent Sessions 迭代计划 v0.6：Relay/Daemon 可靠性与 Terminal 签名认证

> 状态：`done / 2026-08-25`
> 本文是实施计划，不表示代码已经交付。v0.6 开工前必须先完成 v0.5.next 的实施记录回填、证据审计和基线回归；真实 Provider/真实模型的结果继续按 `blocked`、`partial` 或 `passed` 如实记录。
> 计划修订：本版本替换原“Gin + Redis + Kafka + GORM”技术栈迁移方案。当前仓库的权威事实仍是 Gin + `modernc.org/sqlite` + 编号 SQL 迁移 + 进程内可重建状态；本迭代不凭计划引入新的基础设施。
> 收口：P0–P4 全部交付，本地发布门 `task test:v06` 全绿；实施证据与决策记录见[实施记录 13](../实施记录/13-v0.6-Relay-Daemon可靠性与Terminal签名.md)。中间件结论为 `deferred`。原 deferred 残余项"生产 Daemon 签名私钥接线"已于 2026-08-26 按 RELEASE-V06-02 收口（`restart.sh --terminal-signing` + 环境契约 + fail-closed 语义），详见实施记录 13"残余项收口"章节。

## 1. 为什么需要修改原 v0.6 计划

原计划把 GORM、Redis、Kafka 作为 v0.6 的既定交付，和当前仓库事实及已接受 ADR 存在四个问题：

1. **ADR 编号已被占用。** `ADR-012` 已用于 Terminal 认证 TTL 桥接与设备密钥签名终态，不能再创建“ADR-012-Go 后端中间件”覆盖它。
2. **架构决策尚未支持运行时迁移。** `ADR-001`、`ADR-006` 和 `ADR-008` 当前明确采用 SQLite 权威存储、进程内 presence，并以零外部依赖作为单租户自托管的取舍。仅凭计划修改这些 ADR 会把“候选方向”误写成“已验证决策”。
3. **没有需求或测量证明需要 Kafka/GORM/Redis。** 当前瓶颈是 Terminal 身份终态、Relay-Daemon 命令流恢复、fencing、outbox 可靠性和发布证据，而不是 ORM 或跨实例消息总线。SQLite 也不能因为增加 Redis/Kafka 就获得安全的多实例写扩展。
4. **原计划范围过大且验证成本失控。** 同一迭代同时更换存储访问方式、presence、事件总线和部署拓扑，会让回归失败无法归因，也会破坏“本地零外部依赖启动”的既有门禁。

因此，v0.6 改为一次**面向现有架构的可靠性收口迭代**：先把已接受的协议和安全终态做实，再以数据和独立 ADR 决定未来是否引入中间件。

## 2. 目标与成功标准

### 2.1 本轮目标

- 完成 Terminal 从 24 小时 bearer TTL 桥接到设备密钥挑战签名的协议、兼容窗口和回滚路径；设备撤销仍然即时生效。
- 固化 Daemon 专用 REST + SSE 命令流：hello、heartbeat、命令游标、ack/result、断线重连、重复投递、旧 instance、旧 lease epoch 和协议版本拒绝。
- 使 Relay 与 Daemon 两侧 SQLite outbox 的状态转换、重放、失败保留和密文边界可验证；不以“标记 done”代替投递成功。
- 补齐 Relay/Daemon 重启、数据库备份恢复、迁移回滚、进程树清理、脱敏和可观测性证据。
- 保持客户端公开契约、E2EE 边界、Android 唯一写控制权和本地零外部依赖启动不变。

### 2.2 成功标准

1. 新版 Daemon 可以在签名模式下完成 hello、heartbeat、命令 ack/result 和事件上传；旧 bearer Daemon 在 N/N-1 兼容窗口内仍能工作。
2. 重复 nonce、过期时间戳、错误设备、错误 body hash、错误协议版本和撤销设备均 fail-closed，且不会执行命令。
3. Relay/Daemon 重启或 SSE 断线后，历史 cursor 和 pending outbox 可以安全恢复；同一个幂等键不会产生第二个 Provider 动作。
4. 任何进入 Relay 的会话正文、工具参数、文件内容和密钥仍然只能以既有加密 envelope 存储或传输。
5. `task check`、`task test:relay`、`task test:daemon`、`task test:e2e:relay`、`task test:restart` 和相关 Flutter/Adapter 回归均有实际报告；未授权的真实 gate 不得被 fixture 结果替代。

## 3. 当前基线与前置条件

### 3.1 当前事实

- HTTP 使用 Gin；当前账号级和 Daemon 专用实时读取使用 REST + SSE，没有把 WebSocket 当作已交付能力。
- Relay SQLite 是账号、设备、会话、事件、命令、ControlLease 和 Relay outbox 的权威存储；Daemon SQLite 只保存本机状态和本机 outbox。
- presence、限流和广播提示为进程内可重建状态；`RELAY-REDIS-01` 的名称是历史测试 ID，不表示当前依赖 Redis。
- 迁移由 `internal/store/migrate.go` 的编号 SQL 管理；GORM 不在当前依赖或领域端口中。
- Daemon 命令流已经有 `/v1/daemon/hello`、`/v1/daemon/heartbeat`、`/v1/daemon/commands/stream`、ack/result 和事件上传的实现与契约测试；v0.6 的任务是收口边界和可靠性，不重新设计成 Kafka。
- Terminal 当前存在 24 小时 access TTL 桥接，设备撤销逐请求生效；设备密钥签名是 `ADR-012` 记录的后续终态。
- v0.5.next 已有 DSH P0–P4 的实现提交和本地/真实桥证据，但实施记录仍需核对当前提交、报告和覆盖矩阵，不能直接把单次真实模型往返称为完整 Provider gate。

## 4. 范围边界

### 4.1 纳入

- Terminal 签名认证协议和设备公钥登记/撤销流程。
- Daemon hello、heartbeat、命令 SSE、ack/result、事件上传的版本协商、签名校验、重放保护和幂等。
- Relay/Daemon SQLite outbox 的可靠状态机、重试窗口、cursor 恢复、密文审计和迁移测试。
- 备份恢复、迁移回滚、日志脱敏、健康检查、进程树和长连接资源回收。
- 根因层单元/集成/契约测试，以及一个本地 Relay-Daemon-Adapter 纵向回归。
- ADR、OpenAPI/JSON Schema、测试注册表、自动化测试文档和 v0.6 实施记录回填。

### 4.2 明确不纳入

- 不引入 GORM，不替换手写 SQL，不新增第二套 `store.Repository` 实现。
- 不引入 Redis、Kafka、PostgreSQL、NATS、Temporal 或其它运行时基础设施。
- 不把 Daemon 命令流改成 Kafka，也不把 presence、lease epoch、命令状态或事件历史放到外部缓存。
- 不新增 WebSocket 默认传输，不修改 Android/Web/Admin 的产品行为。
- 不修改公开业务语义来掩盖签名认证尚未完成；新协议字段只能 additive，并保留明确的版本拒绝错误。
- 不在本轮做水平扩容、云托管、生产多节点编排或真实模型能力扩展。

未来如确实出现跨 Relay 多实例、吞吐或异步投影需求，必须先提交独立的中间件评估 ADR，附带负载数据、故障模型、运维成本、备份恢复和回滚证据；该 ADR 不属于本 v0.6 交付物。

## 5. 目标协议与安全约束

### 5.1 Terminal 签名认证

签名协议在实现前冻结 canonical bytes，不允许各 handler 自行拼接字符串。建议最小字段为：

```text
protocol_version | device_id | request_method | request_path |
timestamp_ms | nonce | sha256(body) | key_id
```

约束如下：

- 设备在配对/升级流程中生成或确认 Ed25519 身份密钥；Relay 只保存公钥、key id、设备状态和脱敏元数据。
- hello 使用一次性 challenge；heartbeat、命令 ack/result 和事件上传携带时间戳、nonce、key id 和签名。
- Relay 校验设备归属、设备 active 状态、协议版本、时间窗口、body hash、nonce 一次性使用和签名；任何一步失败都不得进入业务处理。
- ControlLease 的 epoch 仍由 Relay SQLite 事务决定；签名只证明设备身份，不能替代 owner、scope、lease 或 idempotency 校验。
- 旧 bearer Daemon 仅在明确的 N/N-1 兼容窗口内接受；窗口结束后返回稳定的 `UPGRADE_REQUIRED`。签名模式失败不能静默回退 bearer。
- 设备撤销必须立即拒绝新请求并关闭旧 SSE；密钥轮换只允许新旧 key 在短暂兼容窗口内双读，一写。
- nonce/challenge 的持久化和清理必须能跨 Relay 重启验证；不能以单机内存状态作为唯一的重放防线。

### 5.2 Outbox 与事件边界

- 业务事实、命令终态、lease epoch 和事件序号先在同一个 SQLite 事务内提交；outbox 记录与业务写入同事务。
- outbox 只有在目标动作获得明确确认后才能进入 delivered；网络断开、响应损坏、超时或进程退出都必须保留 pending/failed 记录并可重试。
- 重试必须有上限、退避、attempts、最后错误的脱敏分类和人工/自动恢复入口；不能无限忙循环。
- Daemon 发送给 Relay 的事件 outbox 只接受 opaque 加密 envelope；Relay 和日志不得出现 Provider 明文。
- 消费或回放以 `event_id`、`command_id`、`request_id` 和 cursor 去重；重启不能产生重复 Provider 动作或重复聚合。

## 6. 分阶段实施计划

### P0：基线、协议冻结与 v0.5.next 收口

**产出：**

1. 回填 v0.5.next 实施记录和 DSH 覆盖矩阵，明确 lifecycle passed、真实模型 round-trip passed 与完整模型能力 gate 的差异。
2. 在 `ADR-012` 中补充签名协议的字段、canonical bytes、N/N-1 窗口、bearer 回滚和设备密钥轮换；不创建同编号 ADR。
3. 在 OpenAPI/JSON Schema 中新增或修订签名 handshake、错误码和能力字段；生成 Go/TypeScript/Dart 产物并验证无漂移。
4. 为签名认证建立脱敏 fixture、错误 fixture 和 replay fixture；禁止将真实密钥、token 或正文写入 fixture。

**退出条件：** 文档、schema、测试注册表和 ADR 相互引用正确；旧 bearer 基线和签名失败行为有明确 oracle；`task check` 通过。

### P1：Terminal 签名认证最小闭环

按“登记公钥 → challenge → signed hello → signed heartbeat → signed ack/result/event → revoke”顺序实现，每个切片先跑根因测试，再接入纵向测试。

1. 实现 key id、公钥登记、设备撤销和轮换的 domain/store 端口；保留旧 token 路径作为兼容实现。
2. 实现 canonical signing/verification helper，统一 body hash、时间窗口、nonce 和错误分类。
3. 将校验接入 hello、heartbeat、command ack/result 和 event upload；handler 只做绑定、鉴权和错误映射。
4. 在失败路径确认不会产生 command 状态变化、lease 变化、事件序号推进或 outbox 副作用。
5. 补充跨进程/重启场景：challenge 或 nonce 未完成时 Relay 重启必须返回可理解的重试错误，而不是接受重复签名。

**退出条件：** 正常签名闭环、旧客户端 N-1 闭环、撤销、重放、错签名、过期、scope/lease 冲突均通过；签名模式没有未经授权的 bearer 静默回退。

### P2：命令流、fencing 与 outbox 可靠性

1. 验证 Daemon hello 返回协商版本、heartbeat 周期、Terminal 游标和 capability 摘要；未知低版本/高版本分别映射稳定错误。
2. 验证 command SSE 的 `after_delivery_seq` 恢复、心跳、客户端取消、慢客户端、断线退避和重复 ack/result。
3. 将命令处理固定为 accepted → running → succeeded/failed/cancelled/rejected/expired；旧 instance、旧 epoch、撤销设备和错误幂等键全部 fail-closed。
4. 为 Relay/Daemon outbox 增加或校验 pending、in-flight、delivered、failed 的状态约束、attempts、退避和重启恢复。只做 additive migration，不用 ORM AutoMigrate。
5. 对事件上传验证“先在本地 outbox 持久化、Relay 确认后再 delivered”；模拟响应丢失、Relay 重启、重复 event_id 和损坏 envelope。

**退出条件：** `task test:e2e:relay` 覆盖 start/send/resume/abort/kill、断线重连、Relay/Daemon 重启和 outbox 重放；任何未确认的命令都不会被错误标记为 delivered。

### P3：恢复、安全和可观测性收口

1. 演练空库迁移、上一版本数据库升级、备份恢复、损坏数据库诊断和 additive migration 回滚。
2. 检查日志、trace、SQLite、SSE 错误、报告和截图中的 token、签名、正文、工具参数、diff 和密文明文泄漏。
3. 检查长连接、provider 进程、进程组、重试 timer、文件句柄和 context 在正常退出、崩溃、超时和重复 stop 后全部释放。
4. 补齐 `/healthz`/`/readyz`、request/trace id、认证失败分类、outbox backlog、重试次数和 SSE reconnect 等不含正文的指标。
5. 进行受限 soak/并发诊断，记录 SQLite busy/锁等待、事件延迟、outbox backlog 和资源上限；不以未经授权的生产性能目标替代结果。

**退出条件：** 恢复和回滚有命令与报告，安全扫描无明文，进程/连接资源无泄漏，性能结论能说明当前 SQLite 架构是否满足单租户范围。

### P4：发布门与未来中间件决策门

1. 更新 `docs/zh/实施记录/13-v0.6-Relay-Daemon可靠性与Terminal签名.md`，逐项记录需求、测试 ID、命令、报告、失败分类、回滚和残余风险。
2. 完成一次从旧 bearer 兼容模式到签名模式、再回到旧模式的本地回滚演练；回滚不得删除 key、事件、命令或 outbox 历史。
3. 运行完整本地门禁：`task check`、`task test:protocol`、`task test:crypto`、`task test:relay`、`task test:daemon`、`task test:e2e:relay`、`task test:restart`，并按需运行 `task test:android`、Adapter 和 headed gate。
4. 仅在 P3 的数据证明存在明确多实例/吞吐需求时，新增“中间件评估记录”；没有数据则将 Redis/Kafka/GORM 维持为 `deferred`，不得因计划完成而引入依赖。

**退出条件：** 本地 release gate 通过；真实 Provider、真实模型、物理 Android 或签名发布缺凭据时有独立 blocked 证据；中间件的最终结论是 `adopted`、`deferred` 或 `rejected` 之一，并附理由。

### 8.2 回滚顺序

1. 签名协议只通过 capability/feature flag 开启，默认保留已验证的 bearer bridge，不能删除旧字段。
2. 签名校验异常时拒绝当前请求并保留诊断，不自动降级；只有明确的兼容版本和已登记的旧客户端才走 bearer。
3. migration 只做 additive change；发布前复制 SQLite 文件并验证恢复；失败时停止新版本，不回写或删除历史事件。
4. 关闭签名 feature flag 后，旧 Daemon 使用 N-1 bearer；ControlLease、event_seq、command idempotency 和 E2EE 数据格式不变。
5. 任何回滚都必须重新执行签名失败、设备撤销、命令幂等和 outbox 重放测试。

## 9. 风险与明确结论

| 风险 | 缓解 |
| --- | --- |
| 签名 canonical bytes 在多端漂移 | 单一 schema/fixture、跨语言 golden vector、禁止 handler 自拼 |
| nonce/challenge 仅存内存导致重启重放 | SQLite 持久化一次性状态或等价事务约束，增加重启测试 |
| bearer 与签名双轨扩大攻击面 | N/N-1 明确截止版本、能力协商、签名失败不静默回退 |
| outbox 被错误标记完成 | 只有明确 ack/响应才 delivered；故障注入和重启重放 |
| SQLite 锁竞争或性能不足 | P3 真实测量；达到阈值再开数据库/中间件 ADR，不在本轮预先迁移 |
| v0.5.next 证据状态滞后 | P0 先做实施记录与报告审计，禁止用提交标题代替 gate |
| 真实 Provider/模型无授权 | 本地 fixture 完成本轮安全范围，真实 gate 标记 blocked，不伪造通过 |

**结论：** v0.6 不再以“换一套 Go 后端技术栈”作为完成定义。完成定义是：在当前 SQLite/Gin/REST+SSE 架构上，Terminal 签名认证、命令流恢复、fencing、outbox、恢复和发布证据达到可审计状态；是否采用 GORM、Redis 或 Kafka 留待有数据后另行决策。

## 10. 完成定义

- `ADR-012`、协议 schema、生成物、测试注册表、项目文档和实施记录一致。
- 签名模式和旧 bearer 兼容窗口均有根因测试、跨层报告和回滚证据。
- Relay/Daemon 重启、SSE 断线、outbox 重放、设备撤销、旧 instance/epoch 和损坏 envelope 均 fail-closed 或可恢复。
- 本地默认启动仍只需要 Relay + SQLite；没有新增 Redis/Kafka/GORM 依赖或 Compose 服务。
- 真实 Provider/模型/物理 Android/生产发布签名不属于默认本地完成条件，未授权时必须独立标记 `blocked`。
- 中间件评估结论单独记录为 `deferred`/`adopted`/`rejected`，不能通过“计划中写了依赖”来预先宣称采用。
