## 1. 诊断基线

### 1.1 现象与控件门控链路

控件本体：`apps/mobile/lib/ui/session_screens.dart:4895-4970` `_ComposerControlStrip`（key `composer-permission-mode-select`）。可用性由三个条件联合决定：

1. **显示**：`controls.availablePermissionModes.isNotEmpty || capability('permission_mode').isSupported`（`session_screens.dart:4911-4914`）——dsh 把 `permission_mode` 声明为 native（`internal/adapter/dsh/adapter.go:414-421`），所以 dsh 会话**恒显示**该控件；
2. **可点**：`permissionModeBlocked == null && controls.availablePermissionModes.isNotEmpty`（`session_screens.dart:4942-4944`）——**目录为空时 `items` 为 0 且 `onChanged: null`**，控件禁用；
3. **目录来源**：`GET /v1/sessions/:id/controls`（`internal/httpapi/handlers.go:673-686`）读取 Relay 会话行 `permission_mode`/`available_permission_modes` 列；**目录为 `[]` 时不下发字段**（契约如此，防冒充可点）。

截图会话是 dsh（`nemotron-3-ultra-free` 为 DSH 桥经 opencode-zen 的默认模型），满足条件 1、不满足条件 2 → "可见但禁用"的空壳。这就是"大多数会话不能用"的直接形状。

### 1.2 根因 A：目录事实只存在于 live handle，历史会话永远没有目录

会话级 mode 目录的唯一事实源是桥在 `session/new|load|resume` 响应里回带的 `modes`（`internal/adapter/dsh/handle.go:655-721` → `extension_handle.go:61-90` `storeModes`）。Daemon 只在**三个时机**把它上行到 Relay：`startSession`（`internal/daemon/runner.go:381`）、`resume`（`runner.go:816`）、`set_mode` 成功后（`runner.go:1611`），且都要求 live handle 实现 `SessionModeHandle`（`runner.go:206-224`，全仓库仅 dsh 实现，`internal/adapter/spi.go:278-282`）。

后果：**v0.8.5 升级前创建、升级后从未 start/resume 过的会话，Relay 行里 `available_permission_modes` 恒为 `'[]'`**（列默认值，`internal/store/migrate.go:457-463`）→ controls 恒不下发 → 移动端恒禁用。用户的大多数会话正属此类。目录没有也不允许凭空回填（事实在桥里，桥进程不跑就没有事实），但"跑一次即可补齐"的路径目前既不通畅（根因 B）也不可知（根因 C）。

### 1.3 根因 B：start/resume 之后 controls 不刷新，目录到达时机错误

移动端只在**打开会话页时拉一次 controls**（`session_controller.dart:2040`）；此后只有**回合完成**才刷新（`_refreshControlsAfterTurn`，`session_controller.dart:2239`）。`startSelectedSession`/resume 命令受理与回执后**不刷新 controls**（`session_controller.dart:849-871`）。

后果：用户对一个历史会话点"启动"（或发消息触发自动启动，`session_controller.dart:952-960`）→ Daemon `startSession` 已完成 `syncModeInfo` 上行 → **但移动端要等整个回合结束（免费模型常见 30-60s）或重进会话页才能拿到目录**。用户在启动后的第一回合里看到的仍是禁用空壳，感知即"点了也没用"。

### 1.4 根因 C：禁用无原因，违反 v0.8.5 完成标准的承诺

`controlBlockedReason('permission_mode')`（`session_controller.dart:1322-1337`）只覆盖 capability unsupported、只读设备、未选会话三种；**capability 支持但目录为空时返回 null**，UI 侧 `onChanged: null` 直接禁用，无 helperText、无 tooltip、无任何文案。v0.8.5 §2.2-2 明确要求"目录缺失时控件禁用**且显示原因**，不再是无解释空壳"，§7 风险表也把"禁用必须附原因 tooltip"列为缓解项——实际只交付了 capability 层的原因，目录层的原因缺失。用户无法知道"为什么灰"以及"怎样才能变可用"。

### 1.5 根因 D：`current_mode_update` 不回传 Relay，当前 mode 值会漂移

桥侧（含 dsh 终端）切换 mode 后发出的 `current_mode_update` 通知只更新句柄内存快照（`internal/adapter/dsh/handle.go:871-886`），**不触发 `syncModeInfo` 上行**；移动端 `selectPermissionMode` 提交成功后的乐观本地态也只写在客户端（`session_controller.dart:1833`）。任一路径之后，Relay/其它客户端读到的 `permission_mode` 都是旧值，直到下一次 start/resume/set_mode。同一会话在移动端与 dsh 终端两侧操作时必然出现口径漂移。

### 1.6 非 dsh 会话：入口整体隐藏是 fail-closed 设计，但同样"无解释"

claude 全量 unsupported（`internal/adapter/claude/claude.go:52-68`，transport 未接入）；codex native 集不含 `permission_mode`（`internal/adapter/codex/codex.go:89-93`）；opencode 未实现 permission 决策与 mode（`internal/adapter/opencode/adapter.go:110-113`）；openclaw 同理。这些会话不满足 §1.1 条件 1 → **控件整体不渲染**。能力真相如此，不伪造；但用户视角是"有的会话连入口都没有"，本轮只在会话信息页补一条如实的只读说明，不做能力伪造（见 §3.5 裁决）。

### 1.7 A 组缺陷：回合无后续、消息双气泡、状态行恒"空闲"（2026-09-05 实测 + debug 留档）

实测会话：dsh / `nemotron-3-ultra-free` / foshan-loupan-tracker。Debug 事实链（Relay canonical 轨迹，共 224 序）：

- seq 222（18:42:31.359Z）turn 1（"这个是什么项目"）正常完成（`completed_turn=true`）；
- seq 223（18:42:56.203Z）user_message"看看天德华府的最新情况"；seq 224（18:42:56.236Z）turnPhase（回合启动）；
- **此后 8 小时事件流完全终止**：无 step/thinking/tool/assistant、无 turn 终态、无 session_error；会话状态 `idle`、最后活动 = 发送时刻。导出 debug 时（09-05 02:41）UI 仍显示"模型仍在处理当前轮次..."。

#### ① 为什么没有后续（根因缺陷）

回合在执行端静默失联：桥已接受 prompt（seq 224 turnPhase 证明回合启动），但上游（opencode-zen 免费池）未产出任何事件，且**没有任何一层把"失联"变成事实**：

1. **桥→daemon**：上游挂起/429/静默失败时，桥未发出 ACP error 或回合终止通知（错误映射缺口，需在 deepseek-harness 侧审计 `session/prompt` 生命周期是否所有失败路径都有出口）。**重试方向已裁决（2026-09-05）：上游瞬时失败由 dsh 桥有界自动重试并发出可见重试事件；daemon 看门狗只作最后兜底（详见 §3.6）**；
2. **daemon→客户端**：daemon 没有回合超时看门狗——回合启动后无论多久无事件，都不会产生 `turn.failed`/`session_error` 事实事件。注意：daemon 本机 outbox 存在 failed 死信史（工作区在飞的 `daemon run --requeue-failed-events` 恢复入口即为其产物），**"事件已产生但上行 Relay 失败被死信"与"上游根本无产出"两种假设 P0 必须盘点区分**（查 daemon 本机库 seq>224 的本地事件与 outbox 状态）；
3. **客户端兜底缺失**：`session_controller.dart` 的回合轮询有硬上限——前台 120×500ms（60s）+ 后台 `_pollTurnCompletionInBackground` 120×500ms（60s），共约 2 分钟；窗口耗尽后**静默放弃且 `_turnInFlight` 保持 true**（`session_controller.dart:2290-2316` 放弃分支不复位、不提示）→ "模型仍在处理当前轮次..."（`session_chat_view.dart:449`，phase 投影为 null 的回退文案）永久驻留。v0.8.1 #5 把窗口从 15s 加到 60s 时只考虑了"慢"，没考虑"永不终态"。

#### ② 为什么发了两条信息

**Relay canonical 轨迹只有一条 user_message（seq 223）**——不是两次成功投递，是客户端渲染层重复：1 条 canonical 气泡 + 1 条未清账的乐观回显气泡。诱因链：回合无后续（①）→ 用户重发同文本 → send 幂等键 `send:$sessionId:$lastSequence:$trimmed`（`session_controller.dart:1063` 附近）两次完全相同 → Relay 幂等去重，不再产生新的 canonical 事件 → 客户端第二次发送重置的乐观回显进入清账等待。清账条件本身按"时间线存在同文本 user_message"匹配（`_mergeSnapshot`，`session_controller.dart:2451-2460`），理论上应能命中 seq 223；实机未清说明存在时序或匹配缺口（候选：第二次 pending 设置晚于最后一次 merge、轮询已放弃不再 merge；或渲染层以 `message_id` 为 key 而该字段为空——debug 中 seq 223 的 `message_id=` 为空）。精确触发路径 P0 复现定案；既有遗留问题 2026-09-02 #1（乐观回显清账失效）与此同源，一并收口。

#### ③ 为什么模型状态永远不会更新

顶部状态行显示的是 Relay 会话行投影 `session.status`：turn 1 完成后置 idle；turn 2 启动后没有任何 canonical 事件更新它 → **恒"空闲"**。"已连接 · v0.0.1 · 可操作"是 Provider 能力行（正常）。两个矛盾表面同屏：状态行说"空闲"、状态条说"处理中"。缺口：

1. 会话状态行不消费 v0.8.4 已有的 `turn.phase` 事件（ADR-015 链路已通，seq 224 就是 turnPhase）——状态行只在 step/终态事件到来时变化，"回合已启动但无 step"的窗口期显示失真；
2. phase 状态条（`session_chat_view.dart:436-460`）对 seq 224 的 phase 投影解析出 null，回退通用文案——启动相位未被识别（P0 盘点该事件的 phase 载荷）；
3. 与 ① 同根：执行端失联时状态机没有任何输入，且无看门狗超时把状态收敛为"失败"。

三项关系：**① 是根因，② ③ 是放大器**（状态行"空闲"误导用户重发 → 重发触发双气泡）。修复必须三者一起收口，只修 ② ③ 不修 ①，用户仍会无限等待。

### 1.8 主页卡片化：按终端机器分卡，同步免抽屉（2026-09-05 需求）

**现状**：主页 `SessionHomeScreen`（`session_screens.dart:43-108`，标题"DSH 工作区"）是**扁平工作区列表**（`_DSHWorkspaceGroup` 每工作区一行，可展开会话），与终端无视觉关联；同步入口是单个全局按钮（`_DSHWorkspaceToolbar`，`session_screens.dart:601-614`）→ **必须先弹出底部抽屉** `_DSHWorkspaceSyncSheet`（`session_screens.dart:1442-1580`：列在线终端单选 → "确认同步"）→ 才调用 `sessions.syncDSHWorkspaces(terminalId:)`。单终端场景下抽屉是纯多余一步（唯一候选自动选中，用户仍需再点一次确认）。

**需求**：主页改为**卡片流，每个卡片 = 一台终端机器**；卡片头部展示终端名（hostname）、平台、在线状态与该卡"同步"按钮，**点击同步直接对该终端发起工作区同步，不再弹抽屉**；卡片体列出该终端下的工作区（沿用现有展开/会话数/搜索语义）。

**数据面已就绪（无需协议改动）**：`MobileWorkspace.terminalId` 已携带工作区→终端归属（`session_models.dart:242`）；`TerminalStatusController` 已提供终端列表、在线态与 `dsh_workspace_sync` 能力判定（`_DSHWorkspaceSyncSheetState._eligibleTerminals` 的判定逻辑上移到卡片层即可）；同步状态机（`workspaceSyncState`/`workspaceSyncWaiting`/`stopWaitingForDSHWorkspaceSync`）按 terminalId 复用。

**待裁决项（P0）**：
1. 卡片同步的进行时/结果反馈：抽屉里的"等待终端响应/同步完成/未完成"文案改为卡片内联状态条 + 现有 SnackBar 是否保留；
2. 多终端各自同步的并发口径：逐卡串行（同一时间只允许一个同步在途，其余按钮禁用并提示）还是允许并行——建议先串行，避免 `workspaceSyncState` 单槽状态机被并行请求互踩；
3. `terminalId` 为空的存量工作区归组（"未归属"卡 vs 隐藏）；离线/能力缺失终端的卡片降级展示（灰态 + 原因，保留 fail-closed 语义，不伪造可点按钮——与 §3.3 禁用原因口径一致）；
4. 全局同步按钮与抽屉的去留（建议移除，命令面板/下拉刷新保留全量刷新语义）；下拉 `RefreshIndicator` 改为刷新全部终端状态 + 工作区。

### 1.9 会话消息 Markdown 渲染补全（2026-09-05 需求）

**现状**：助手消息已有一个手写迷你渲染器（`session_chat_node_seat.dart`，key `session-assistant-markdown`），仅支持：围栏代码块、`# `/`## ` 两级标题、`- `/`* ` 无序列表、行内 `**粗体**` 与 `` `代码` ``。**缺失：三级及以下标题（`###`）、表格（`|---|`，模型高频输出）、有序列表、嵌套列表、引用块、链接、水平线**——截图实机中 `### 状态统计` 与房源表格全部裸文本显示，可读性差。

**需求**：会话消息（至少 assistant 侧）支持完整 Markdown 渲染，与模型实际输出语法面（GFM：标题/表格/列表/粗斜体/行内代码/链接/引用）对齐。

**待裁决项（P0）**：
1. **实现路线**：继续手写扩展（可控但语法边界多、回归重）vs 引入成熟解析库（`markdown` 包 AST + 自建 Widget builder；`flutter_markdown` 官方已停止维护需评估社区替代）。新依赖引入需按仓库惯例评审。
2. **display-safe 边界（fail-closed，沿用仓库口径）**：不渲染原始 HTML；图片不自动加载（不发网络请求，显示占位）；链接点击需确认或仅复制，不静默外跳。
3. **流式渲染策略**：assistantMessage 事件为流式累积前缀（实测 seq46-219 每条全量增长），partial Markdown（未闭合 `**`、未完成表格行）会闪烁跳变——裁决：流式中未闭合语法降级为普通文本 + 表格按行增量渲染，或流式纯文本、终态后整段 Markdown 重渲染。
4. **性能**：长回复 + 每条 delta 全量重解析需节流（如 ≥100ms 合并重渲染）。
5. **范围**：user 消息建议保持纯文本；轨迹视图与 debug 导出保持纯文本；Web 端（ChatView.vue）是否同步支持另列或本期一并（P0 裁决）。

### 1.10 消息"复制"按钮全覆盖（2026-09-05 需求）

**现状**：每条消息下方的操作行已有复制按钮（`session_chat_node_seat.dart:573-582`，key `session-message-copy-<seq>`，复制后内联"已复制"反馈），但由投影层 `canCopy` 严格门控（`session_projection_controller.dart:252-261`）：user 恒可复制；**assistant 仅在 `completedTurn=true` 时**；tool/思考/通知/其余节点一律不可复制。

**缺口**：① 流式中的 assistant 消息没有复制按钮——用户想复制已生成的部分做不到；② A 组①类"永远等不到终态"的回合（文本其实已流式产出完毕）**永久没有**复制按钮；③ 工具命令/输出、思考摘要、系统通知等节点无法一键复制，用户只能手动选择文本。

**需求**：每一个会话消息（有可复制文本的节点）下方都有"复制"按钮。

**待裁决项（P0）**：
1. 节点类型覆盖面：assistant 含流式中（复制当前已生成前缀）之外，tool 命令/输出、思考摘要、notice、question 等是否全部覆盖，或仅 assistant+user+tool 三类；
2. 大文本截断口径：tool 输出可能极长，复制全文还是截断（如 ≤64KB）并提示；
3. `completedTurn` 门控移除后，A 组①卡死回合的已产出文本即可复制（与 G6 看门狗正交，先行收益）；pendingSteering 乐观回显维持现有口径（仅 user）；
4. Web 端是否对齐（P0 裁决）。

## 2. 目标与完成标准

### 2.1 目标

- G1（目录可达）：任一 dsh 会话经一次 start/resume 后，其 mode 目录在 controls 可见且移动端下拉可选可切换；"历史会话 → 启动 → 目录到达"全路径在真实链路验证。
- G2（时机正确）：start/resume 命令回执后客户端立即刷新 controls，目录在启动完成后的秒级到达，不等回合结束；`current_mode_update` 后 Relay 与客户端的当前 mode 不再漂移。
- G3（原因可见）：目录为空时控件保持禁用但**附中文原因与恢复路径**（如"权限目录未同步，启动会话后自动获取"）；capability unsupported 的会话在会话信息页如实展示"该 Provider 不支持权限模式"。任何禁用状态都可解释。
- G4（口径一致）：停止会话的 mode.set 在客户端预检拦截并给出原因（服务端 `local_state_missing` 不再作为第一现场暴露）；fixture 与真实契约继续同 schema 门守护。
- G5（承接）：工作区在飞改动独立提交收口；v0.8.5 残余项按 §4-P4/P5 推进（可达成项收口，不可达成项如实保留状态）。
- G6（回合必达终态，A①）：任一已受理的 send 回合必须在有界时间内到达终态——执行端产出事件则按事件收敛；超过看门狗时限（默认可配置，建议 120s 无任何事件即判失败）由 daemon 产生 `turn.failed` + `session_error` 事实事件；客户端轮询窗口耗尽时必须显式收敛为"回合超时，请重试/中断"，不允许永久驻留"处理中"。
- G7（消息不重复，A②）：同一条用户消息在时间线上至多渲染一个气泡；乐观回显在 canonical user_message 合并、命令被拒、轮询放弃三个路径都保证清账或显式提示；重发同文本在"上一回合未终态"时被防抖拦截或转为排队提示。
- G8（状态行一致，A③）：会话状态行消费 turn.phase（ADR-015 既有链路），回合在途时显示"执行中/思考中/工具执行中"等真实相位，不再与"处理中"状态条矛盾；看门狗超时后状态行收敛为"回合失败"。
- G9（主页终端卡片化）：主页按终端机器分卡（终端名/平台/在线态 + 卡内"同步"按钮 + 该终端工作区），点同步直接对该终端发起 `syncDSHWorkspaces(terminalId:)`，不再弹出选择抽屉；离线/能力缺失终端灰态带原因，fail-closed 语义不放宽。
- G10（消息 Markdown 完整渲染）：assistant 消息按 GFM 语法面渲染（多级标题/表格/有序与嵌套列表/引用/链接/行内样式/代码块），流式过程不抛错、终态渲染稳定；不渲染 HTML、不自动加载图片，display-safe 边界不放宽。
- G11（复制按钮全覆盖）：每个有可复制文本的会话消息节点下方都有"复制"按钮（含流式中的 assistant、未终态回合的已产出文本、tool/思考/通知按 P0 裁决范围），复制结果与"已复制"反馈口径统一。

### 3.1 mode 目录同步时机扩展（daemon）

- `current_mode_update` 通知处理路径（`handle.go:871-886`）在更新句柄快照后，经既有 `modeInfoSink` 触发一次 `syncModeInfo` 上行；同一回合内多次通知做去抖（如 500ms 窗口合并），上行失败仅记日志（与既有 sink 语义一致）。
- **不做**：无 live handle 时的目录"回填"（没有事实源，伪造即违反 fail-closed）；`session/new` 之外伪造目录；把目录塞进 canonical 事件流（v0.8.3 P3 已裁决 mode 不进事件流，维持）。

### 3.2 controls 刷新时机（Flutter）

- `_submitCommand` 的命令回执等待机制（`_awaitCommandReceipt`）对 `start`/`resume` kind 增加"回执 succeeded 后刷新 controls"钩子；刷新失败静默（下一回合/重进会话仍会兜底），不阻塞启动主流程。
- 目录到达即 `notifyListeners`，下拉从禁用转为可用无需重建页面。

### 3.3 禁用原因可见（Flutter UI）

- 目录为空且 capability 支持时：`InputDecoration.helperText`（或长按 tooltip）展示"权限目录未同步——启动会话后自动获取"；该文案由 controller 新增 `permissionDirectoryHint` 一类 getter 供给，禁止 UI 层自猜。
- capability unsupported 时维持现状（控件不渲染），但会话信息页（`session_info_screens.dart:127-129` 既有"权限模式"行）扩展展示 provider 原因（`capability('permission_mode').reason`）与目录快照，只读、如实。

### 3.4 停止会话 mode.set 预检（Flutter）

- `selectPermissionMode` 提交前按 `selectedSession.status`（stopped）预检，命中即 `_setError('会话未运行，启动后可切换权限模式')` 并保持下拉当前值；不发起必败命令。服务端 `ErrSessionInstanceMissing`（`runner.go:932-940`）语义不变，仅不再作为第一现场。

### 3.5 非 dsh 会话口径（裁决项，P0 定稿）

- 方向：控件隐藏维持（不伪造入口）；解释移至会话信息页只读行。备选（渲染禁用控件 + unsupported 原因）否决——为恒不可用能力渲染可交互形状违反既有 fail-closed UI 约定。

### 3.6 回合看门狗与超时收敛契约（A 组，P0 定稿细节）

- **事实源在 daemon**：回合（send 受理）启动后启动看门狗计时，窗口内 handle 未产出任何事件且未到达终态 → daemon 产生 `turn.failed` + `session_error`（脱敏原因 `回合超时（无事件），上游可能不可用`）两条 canonical 事件并收敛会话状态；任一事件/终态先到即撤防。时限默认 120s，`AGENT_SESSIONS_TURN_WATCHDOG_MS` 可配置，0 = 关闭（回滚开关）。
- **重试责任（2026-09-05 用户裁决）：交给 dsh 桥**。上游瞬时失败（429/超时/断流）由 deepseek-harness 桥内有界自动重试（次数上限 + 退避，可配置）；非瞬时失败（鉴权/配额耗尽/参数拒绝）不重试，直接产出错误事实。**每次重试必须对外可见**——桥发出一条回合相位/通知事件（如"上游失败，第 N 次重试"），客户端状态行显示"重试中"而非静默；该事件同时为 daemon 看门狗续期（有事件即不判超时），避免"桥在重试、看门狗误杀"。Agent Sessions 客户端自身不做自动重试。
- **wire 沿用既有事件类型**：`turn.failed`/`session_error` 均为既有 canonical 类型，不新增 wire 形状，客户端零协议改动即可收到（桥侧重试通知事件按 dsh/* extension / 回合相位既有口径承载）。
- **客户端口径**：轮询窗口（前台 60s + 后台 60s）耗尽仍无终态时，不等 daemon——本地显式收敛为"回合超时，请检查连接或重试"并复位 `_turnInFlight`；随后若 daemon 事实事件迟到，按事件校正（事件优先，本地提示清除）。
- **清账契约（A②）**：乐观回显清账不再依赖"恰好有一次后续 merge"——在轮询放弃、命令拒绝、canonical 合并三条路径都必须收敛；渲染层保证同一 canonical user_message 只画一个气泡。
- **状态投影契约（A③）**：会话状态行消费 turn.phase（ADR-015），在途显示真实相位；`turn.failed` 到达后状态行显示"回合失败"，与状态条同源收敛。

## 7. 风险、回滚与不做事项

| 风险 | 处理与回滚 |
| --- | --- |
| 看门狗时限过短误杀慢回合（免费模型 30-60s 常见） | 时限按"无任何事件"计而非总时长；默认 120s + 可配置；慢回合对照用例（90s 产出）防误报（V086-11）；回滚 = 关闭看门狗开关，退回现行为 |
| 看门狗与 abort/正常终态竞争产生重复失败事件 | 终态先到则看门狗撤防；契约测试锁定"abort 后不重复报" |
| 桥侧重试与看门狗互相干扰（重试中被误判超时，或无限重试永不收敛） | 重试必须发出可见事件为看门狗续期 + 重试次数/总时长有上限；契约测试锁定"重试中不误报、上限耗尽必收敛" |
| 防重拦截误伤合法的"再次提问同文本" | 仅在上一回合未终态时拦截/提示排队，终态后允许重复提问；controller 测试覆盖 |
| 终端卡片并行同步互踩单槽 `workspaceSyncState` | P0 裁决串行单槽：同一时间仅一张卡允许发起同步，其余卡按钮禁用并提示"同步进行中"；回滚 = 恢复全局抽屉入口 |
| Markdown 解析库引入扩大依赖面/安全面 | 新依赖走评审锁版本；HTML 与图片加载显式关闭并有注入用例守护；回滚 = 退回现有迷你渲染器（保留不动或按开关回退） |
| 流式全量重解析造成长回复卡顿 | 重渲染节流合并（≥100ms）+ 只对最后一个增长中的消息节点做 Markdown；性能 smoke 用例 |
| `current_mode_update` 高频触发造成上行风暴 | 回合内去抖合并 + 目录内容不变不重发；回滚 = 通知路径摘除 sink 调用，退回 v0.8.5 三时机行为 |
| 刷新 controls 与会话切换竞态导致旧目录污染新会话 | 沿用 selectionGeneration 防护；测试锁定（V086-03） |
| 原因文案与真实阻塞原因不符（误导用户） | 文案由 controller 统一供给、P0 逐句裁决；不渲染猜测性文案 |
| 历史会话盘点发现占比与根因判断不符 | P0 盘点先行，验收样本按盘点数据定；诊断基线允许按证据修订（留档于实施记录 25） |
| 承接项（漂移套件/Keystore 实机）依赖外部条件不可达成 | 如实标 `blocked` + failure_class，不阻塞主线收口 |
| 在飞改动与本轮改动混叠造成回归盲区 | P0 强制独立提交、独立回归后再开始 P1/P2 |

本期明确不做：非 dsh provider 的 permission/mode 能力实现（依赖各 bridge 协议事实，claude transport 未接入、codex/opencode 无 mode 协议面）、无 live handle 的目录伪造回填、目录进 canonical 事件流、permissions 决策通道改造（v0.8.2 已闭环）、新增 push 通道（本轮只复用回执后拉取）；A 组的自动重试收敛在桥侧（dsh 有界重试），Agent Sessions 客户端与 daemon 均不做自动重试、不做无上限的轮询延长、不做跨 Provider 的通用回合超时协议（先覆盖 dsh + fixture 契约，codex/opencode 看门狗按同一 runner 语义自然获得）。
