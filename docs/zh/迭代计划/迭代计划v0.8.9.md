# Agent Sessions 迭代计划 v0.8.9：Daemon 与 Relay DB 生命周期、命令流和 outbox 可靠性收口

> 状态：`planned（2026-09-06，承接 v0.8.8 遗留问题）`
>
> 前序：[迭代计划 v0.8.8](迭代计划v0.8.8.md)（已交付；能力矩阵、权限三档和 v0.8.8 既有回归保持不变）。本期是可靠性专项，不扩展 Provider 能力，不改变 Flutter 既有轮询、回合收敛、打字机渲染和权限交互语义。

## 1. 诊断基线

### 1.1 已确认的第一条故障链：Relay DB 世代与 Daemon durable state 脱钩

`restart.sh` 的 `reset_default_local_relay_db()` 删除并重建 Relay SQLite，同时删除 token 文件，但不处理 Daemon 本地 `daemon.db` 中的 `relay_commands`、`relay_event_outbox`、`relay_usage_outbox` 和 `relay_delivery_seq`。现有 pairing scope 只绑定 `RELAY_ADDR|RELAY_DB_PATH`，同一路径重建数据库时不会变化。

Daemon 重新配对后，`adoptTerminalIdentity()` 只清零 delivery cursor，不使旧命令和旧 outbox 失效。`runOnce()` 在建立 SSE 之前调用 `processPending()`；旧 `started`/`received` 命令访问新 Relay 时得到 404。`RunWithRetry()` 未把该确定性 404 视为终态，因而按 100ms 到 6400ms 的退避无限重试，SSE 长连接和周期 heartbeat loop 永远没有进入。

证据：

- [restart.sh reset 路径](../../restart.sh:846)
- [Daemon 身份切换](../../internal/daemon/relay.go:864)
- [SSE 建立前的 pending 恢复](../../internal/daemon/relay.go:894)
- [404 的 Relay not found 映射](../../internal/domain/daemon.go:1137)
- [404 被当作可重试错误](../../internal/daemon/relay.go:831)
- [v0.8.8 真实日志](../../../.task/restart/logs/20260905T173434Z/daemon.log:3)

### 1.2 已确认的第二条故障链：SSE reader 被同步执行阻塞

`RelayClient.Stream()` 在 scanner goroutine 中同步调用 `consume()`。`handleDelivery()` 每收到一条 delivery 都触发全量 `processPending()`；后者持有 `processMu`，并在锁内执行网络请求和 Provider 命令。

当 `session.send` 等待 DSH permission 时，后续 `mode.set` 会在 `SessionRunner.executionMu` 上等待。SSE scanner 卡在该回调中，无法读取后续 `permission.approve` 或 abort。连接可能仍然存在，但命令流已经停止消费，形成队头阻塞。

证据：[Stream 回调](../../internal/daemon/relay.go:497)、[delivery 处理](../../internal/daemon/relay.go:977)、[全量 pending 执行](../../internal/daemon/relay.go:1111)、[SIGQUIT 阻塞栈](../../../.task/restart/logs/20260905T175651Z/daemon.log:300)。

### 1.3 已确认的第三条故障链：旧 event outbox 被误判为永久毒丸

Relay DB 重建后，旧 session/command 的事件在新库中不存在。`flushEvents()` 将除 429 外的所有 4xx 都标记为 `RELAY_REJECTED_PERMANENT`，导致旧事件长期堆积为 failed；人工 requeue 后又重复产生 404/400/409 日志。

当前样本：`relay_event_outbox` 为 delivered 6187、failed 2200；`relay_commands` 为 completed 350、started 2。该问题不是 SSE 阻塞的唯一原因，但与世代错位共享同一个生命周期根因。

## 2. 目标与完成标准

### 2.1 目标

- **G1 世代可识别**：每个 Relay DB 实例拥有不可复用的 generation；Daemon 能在启动和运行期间识别 Relay DB 已被重建。
- **G2 本地状态可收口**：generation 变化时，旧的命令、事件、usage outbox 和 delivery cursor 不再参与新 Relay 的执行或上传；旧行保留或清理的策略可审计、可回滚。
- **G3 reset 有生命周期边界**：任何会重建 Relay DB 的 owner bootstrap 路径都不能在受管 Daemon 继续运行时执行；`restart-flutter` 不得静默制造该窗口。
- **G4 404 不再无限重试**：Resolve/Ack/专用 result 的 stale command 404 有明确本地终态和稳定错误码；未知 404 不得被一刀切吞掉。
- **G5 SSE 不被业务执行拖住**：reader 只负责解析、持久化和入队；普通命令、长回合命令和控制命令有独立调度边界，审批/abort 不被 Provider 执行阻塞。
- **G6 outbox 与 generation 一致**：旧世代事件和 usage 不会污染新 Relay；瞬态网络失败仍按原有有界退避重试。
- **G7 不回归**：v0.8.8 能力矩阵、权限三档、附件 fail-closed、文件/Git 只读沙箱和 v0.8.1-v0.8.8 聚合回归保持通过。

### 2.2 完成标准

1. 新增 Relay DB generation 的协议、迁移、hello/heartbeat 返回和 Daemon 本地持久化；字段为 additive，不修改 `events.json` 或既有 command kind。
2. generation 变化或 reset marker 出现时，本地 relay-scoped state 在一个 SQLite 事务中完成隔离/收口；新命令能够在同一进程或受控重启后继续处理。
3. `restart.sh restart`、owner key rotation、owner refresh 重建、owner/daemon pairing 重建均满足“停止 Daemon → reset Relay → 重新配对/确认 workspace → 启动 Daemon”的顺序；`restart-flutter` 在需要 reset 时返回可操作错误或转交完整 restart。
4. stale 404 不产生无限 retry；本地命令落为现有终态模型可表达的 `completed/result_status=failed`，错误码固定为 `RELAY_GENERATION_RESET`，不新增 wire 终态。
5. blocked `session.send` 场景中，`permission.approve/reject`、`session.abort` 和必要的 question answer 能在有界时间内被读取并处理；heartbeat 不因业务执行而停止。
6. event/usage outbox 在世代切换后不再自动 requeue 旧行；旧数据的清理、隔离、失败原因和计数可查询且不泄露密文或 Provider 正文。
7. `task docs:verify`、`task check`、Go/Flutter 受影响回归、`task test:e2e:relay`、`task test:restart` 和 v0.8.8 聚合 gate 按实际可执行口径通过；失败必须分类并保留证据。

## 3. 契约冻结与边界

### 3.1 Relay generation 契约

- Relay 在首次创建数据库时生成随机、不可预测且持久化的 `relay_generation`；同一 SQLite 文件重启不变，删除重建必变。
- `daemon.hello` 和 `daemon.heartbeat` additive 返回 `relay_generation`。Daemon 启动时以 hello 为权威，运行期间以 heartbeat 发现变化。
- generation 不作为客户端业务字段，不进入 session event envelope，不替代 lease epoch，也不改变 Terminal ID、delivery sequence 或 command ID 的语义。
- 旧 Relay 不返回该字段时，Daemon 按明确兼容策略处理：若协议版本允许则进入受控 legacy 模式并记录告警；若无法安全判断世代，则停止命令处理并要求重启，不进行无限重试。

### 3.2 Daemon 本地状态契约

- `local_state` 保存当前 `relay_generation` 和 reset 状态；`relay_commands`、`relay_event_outbox`、`relay_usage_outbox` 增加 generation 关联或等价隔离标识。
- generation 变化的收口操作必须原子完成：停止接收新命令、取消当前 Relay loop context、清理/隔离旧世代行、清零 cursor、清除旧 Terminal 绑定，再进入需要重新配对的状态。
- `command_outbox` 是 Daemon 发起的本地 outbox，与 Relay 下行状态分开；是否保留其中待发送命令必须逐类裁决，不能因清理 relay state 而误删用户动作。
- 不记录 token、密钥、命令正文、Provider 回复、文件路径或 diff 正文。诊断只保留 generation hash/ID 的脱敏形式、数量、状态和错误码。

### 3.3 终态与错误码契约

- 不新增 `abandoned` wire 状态。stale command 在本地使用已有 `completed` 行状态和 `result_status=failed`，`error_code=RELAY_GENERATION_RESET`。
- Resolve/Ack 404 只有在请求上下文确认是当前 generation 的 stale command 时才按上述规则收口；普通 API 404 仍按原错误传播。
- generation reset、认证失效、协议不兼容、网络断开分别记录不同 failure class，不能合并为 transient retry。

### 3.4 SSE 调度契约

- scanner 不调用 Provider、Resolve、事件上传或长时间持锁；接收顺序只保证“落盘后入队”。
- 普通命令使用有界 worker；`session.send` 可异步运行并受当前 loop context 约束。
- `permission.approve/reject`、`session.abort` 和 question answer 属于控制优先队列，不等待普通执行 worker 的 `executionMu`。
- `processMu` 只保护状态转换和去重，不覆盖网络请求或 Provider 执行。

## 8. 风险、回滚与不做事项

| 风险 | 处理与回滚 |
| --- | --- |
| generation 变化误判导致正常 Daemon 被迫重配对 | 先以 additive hello/heartbeat 和只读诊断运行；保留 legacy 开关；回滚只关闭 generation enforcement，不回退已完成的本地迁移 |
| reset 与 Daemon 并发造成半清理 | 使用生命周期锁和“停止 Daemon → reset → pairing → 启动”顺序；发现锁/进程不一致时 fail-closed |
| 清理 relay_commands 造成用户动作丢失 | 先事务性 quarantine 并记录计数；只对明确 stale generation 收口，不删除 command_outbox |
| 404 分类过宽吞掉真实 API 漂移 | 只对带 generation 证据的 Resolve/Ack/result 404 使用 `RELAY_GENERATION_RESET`；其他 404 保留原始失败 |
| worker 并发导致命令重复执行 | 延续 durable `starting/started` 规则；队列去重、command ID 幂等和 shutdown context 回归锁定 |
| 控制优先级破坏 Provider 生命周期 | abort/permission 仍由 handle 的 one-shot/owned 语义校验；只改变调度等待，不绕过终端、workspace、capability fence |
| 旧 outbox 被错误 requeue | generation 过滤优先于 retry；人工恢复入口必须显式选择 generation，默认不恢复旧世代 |
| 可见 gate 受 TCC/窗口/宿主负载影响 | 先完成根因层和 full gate；可见失败标记 `environment_or_startup_failure`，不能用截图替代协议证据 |
| schema/ADR 漂移 | 先冻结字段和错误码，再改实现；每个公开字段同步 OpenAPI、生成物、契约测试和文档 |

本期明确不做：新增 WebSocket、移动端接入 SSE、改变事件 schema、改变 lease epoch 或 fencing 语义、真实 E2EE 移动端解密、Provider 能力扩展、真实 Android/Push/后台服务、Redis/Postgres、多实例 Relay、历史漂移套件和 watch 模式。

## 10. 断点恢复与交付报告

每次 gate 报告必须包含 `suite`、`status`、`report_kind`、测试 ID、版本/behavior hash、fixture revision、命令、`real_browser`、`real_model`、`real_upstream`、`fixture_data`、`local_test`、`headless`、失败分类、artifact 路径和残余风险。恢复只能在 suite、generation 契约、fixture、oracle 和测试版本一致时继续；任一变更都把旧 checkpoint 标记为 stale 并保留。

交付报告按“需求 → 测试 ID → 自动化文件 → 实际命令 → 证据 → 文档回填 → 残余风险”逐项对照。任何只通过截图、HTTP 200、headless、fixture 或部分 gate 的结果，都不能描述为完整交付。
