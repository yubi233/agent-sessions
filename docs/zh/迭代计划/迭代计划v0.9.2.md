### 1.2.1 P0 实测结论（2026-09-16）

- **L1 已实测确认**：云端 Relay `/v1/capabilities` 中 dsh `available=false`，fail-closed 原因 = `未找到 node 运行时: exec: "node": executable file not found in $PATH`（Relay 容器为 scratch 单二进制镜像，无 node/DSH 检出；Detect 结果在进程内 fail-closed 缓存）。探针与报告：`e2e-verify/real/v092-cloud-capabilities-probe.mjs` → `e2e-verify/reports/2026-09-16T03-23-41-244Z/V092-ATTRIB/cloud-capabilities-probe.json`（TLS 指纹钉扎、仅 GET、脱敏）。
- **L2 已实测确认**：daemon 日志 `2026-09-16T07:40:36 … "local_state_missing: session instance 不存在: session=sess_1789514837078…"`（`session.send` 到达 daemon 但无运行句柄）。
- **环境侧成因（已收敛）**：验收环境曾有两个 daemon 进程共用同一 state-dir（06:48/07:24 各一），产生两个同时在线、均 fresh heartbeat 的终端身份（`term_…944`、`term_…474`），命令路由出现歧义；已终止重复实例、收敛为单实例。是否在 P2 增加 state-dir 单实例锁见 §7 T7（待裁决）。
- **本机链路对照通过**：真实桥生命周期测试（`AGENT_SESSIONS_DSH_LIVE=1 go test ./internal/adapter/dsh -run TestLiveBridgeLifecycle`，daemon 同款 cordis 配置）PASS，版本门判定通过；手动桥冒烟 `e2e-verify/real/dsh-acp-smoke.mjs` PASS。证明桥、凭据、版本门在本机（执行侧）均正常，问题不在本机链路。
- **云端数据现状（脱敏盘点）**：终端 3（2 个原 fresh 实例 + 1 个历史 stale）；DSH 工作区 4（全部绑定 `term_1789510181474_terminal`）；DSH 会话 4（2 stopped / 2 idle）。

### 1.2.2 P0 复现矩阵结论（2026-09-16，fixture/local）

入口：`node e2e-verify/real/v092-attribution-matrix.mjs --live`（可重复运行；报告 `e2e-verify/reports/2026-09-16T04-36-52-300Z/V092-ATTRIB/attribution-matrix.json`，**10/10 passed**）。
口径：`local_test=true`、`fixture_data=true`、`real_browser=false`、`headless=false`、`real_model=false`；`--live` 分支使用真实桥子进程做握手/生命周期，但**不发送 prompt**，因此仍不消耗 token。

| 层 | 归因结论 | 钉扎用例 |
| --- | --- | --- |
| L1 | 能力事实源在**进程内**：同一份 `dsh.Adapter` 代码在 Relay 进程（云端 scratch 无 node）fail-closed，在执行侧 Daemon 进程正常（真实桥 `version=0.0.1`、`model_groups=1`）。移动端消费的 `/v1/capabilities` 来自 **Relay 进程**，因此云端必然误判不可用。 | `TestV092DetectIsPerProcessFact`、`TestV092LiveExecutionSideDetect`、`TestLiveBridgeLifecycle` |
| L2 | 会话生命周期：本地 instance 映射（store）与运行句柄（内存）分离。重启后"有映射无句柄"时 send 返回 `ErrSessionInstanceMissing`，且 runner **已补发可见失败链**（user_message → session_error → turn_completed），不是静默失败。**resume（流式）能原样恢复同一 instance 且不触发 `adapter.Start`；start 会新建实例覆盖映射（历史断链）**——这是把移动端"发送前自动恢复"从 start 改到 resume 的判据。 | `TestV092AttribNewSessionBaseline`、`TestV092AttribRestartResumePreservesInstance` |
| L2/安全 | 非流式 adapter 自报 `resumed` 但**未交出可运行句柄**时，runner 仍然 fail-closed（"adapter resume 成功但本机没有可用句柄"），不伪造可用实例。 | `TestV092AttribRestartResumePreservesInstance`（b2 段） |
| L3 | 首次 Detect 结果被永久缓存：传输层失败（无 node）与握手失败两种形态下，**环境修复后同一进程内仍不可用**，且失败缓存命中时不再 spawn（`spawns` 保持 1）。成功缓存同样不重复 spawn（重探测不得退化为每请求重探）。 | `TestV092DetectCacheLocksFailureUntilRestart`、`TestV092DetectCacheLocksHandshakeFailure`、`TestV092DetectCacheHitsAreFree` |
| L2 | 桥异常退出时 send 失败被补发为可见终态，且本地 instance 映射不被改写（恢复必须先 resume）。 | `TestV092AttribBridgeExitVisibleFailure` |
| L1 | 版本门拒绝是显式错误（错误文本含版本值）、不写 instance 映射、不留事件摘要——与"版本门不回退"一致。 | `TestV092AttribVersionGateRejectionIsExplicit` |

结论：**L1 与 L3 是本轮必须修的产品缺陷（云端不可用 + 不可自愈）；L2 的 send 失败可见性已经成立，缺的是"发送前自动恢复走 resume"**；L4 属文档口径问题（P4 收口）。这与 §1.2 各层"代码可证"的初判一致，现在四层都升级为实测确认。

### 1.3 已排除的误判（不进入实现方向）

- “Daemon 不会自动创建会话”不成立：创建/启动链路已存在（`createSession(autoStart:true)`、DSH `Start` 已 spawn 桥并 `session/new`）；**不新增**自动创建逻辑。
- 手工修改 workspace `terminal_id`（验收期曾用于恢复终端路由）不是产品修复；验收禁止重置 SQLite、禁止删改既有账号/工作区/会话数据（2026-09-16 用户指令延续）。
- 凭据文件存在、桥能在前台手动启动，均不能证明 Daemon/Relay **进程内**的 Detect 可用（见 L3）。

## 2. 目标与验收标准

- **G1 事实源一致**：移动端看到的 DSH 可用性与模型目录，必须与**执行该会话的 Daemon/Terminal** 的事实一致；云端 Relay 不再以自身探测结果作为 DSH 的最终事实（具体通道见 §7 T2）。
- **G2 首条发送**：云端拓扑下，手机对 DSH 会话的首条发送可完成并获得终态。
- **G3 重启恢复**：Daemon 重启后，发送前自动恢复走 **resume**，延续原 DSH 实例，不新建、不丢历史。
- **G4 错误可见**：不可用/不可恢复时给出稳定可区分的错误（provider 不可用 / 会话实例缺失 / 版本门 / 环境失败），不伪装成功。
- **G5 缓存可恢复**：Detect 失败不再依赖“重启进程”恢复（受控重探测）。
- **G6 口径分层**：项目文档与验收报告按分层事实表述，“手机 UI → DSH 发送”单列验证状态。

必须观察到：同一会话在（a）云端正常、（b）Daemon 重启、（c）桥异常退出后，手机分别得到“可发送 / 明确恢复或稳定失败 / 稳定失败有终态”的一致结果；恢复后原 instance 保留。

## 3. 影响面与冻结契约

### 3.1 影响模块

`internal/adapter/dsh`（Detect 缓存/重探测、Start/Resume）、`internal/adapterreg`、`internal/daemon`（runner 与上行）、`internal/httpapi` + `internal/relay`（capabilities 与会话视图）、`apps/mobile`（能力门控与发送前恢复）、`deploy/ecs`（如涉及拓扑配置）、`docs/test` 与索引、`e2e-verify`。

### 3.2 冻结契约（实施前必须先冻结）

- **C1 能力事实源**：DSH 的可用性与模型目录以执行侧（Daemon）为准的传递机制，在 P0 证据裁决后冻结；不得以“云端再装一份 DSH / 把凭据放上云”作为默认方案（违背零凭据注入与隔离口径）。
- **C2 重探测**：DSH Adapter 具备受控 re-probe 路径（触发条件集中、可注入测试），失败原因可查询；不得无条件每请求重探（握手 spawn 有成本）。
- **C3 start/resume 语义**：新会话 = start；已有 instance 映射且无运行句柄 = resume；失败显式可见；移动端自动恢复行为与 Daemon 一致（注释/文案同步修正）。
- **C4 幂等与并发**：重复 start 回收旧句柄（DCM-03 语义保留）；同一会话恢复 single-flight；已提交消息不盲目重放。
- **C5 安全不回退**：版本门、trusted proxies、lease fencing、workspace 确认边界不因本期放宽。
- **C6 数据**：不重置 SQLite；不新增破坏性迁移；如确需数据修复，单列备份/预览/授权方案。

### 8.2 本轮实际修复的真实缺陷（超出计划范围，均由实测暴露）

1. **Relay→Daemon 命令投递契约**（P2/P3）：Relay 把 `session_id` 作为命令顶层字段下发，Daemon 的 `Command` 结构没有该字段、runner 又只从 payload 读，导致除 `session.send` 外的全部会话命令以「缺少 session_id」失败；同时 payload 缺 envelope 层使 `model` 读不到。修复后 `session.model_select/start/resume` 在真机链路返回 `succeeded`。
2. **多 Daemon 实例命令竞争**：见 T7。
3. **Android 物理设备 gate 作用域缺陷**：`cloud` 变量在 try 内声明而 finally 报告块使用，导致整个真机 gate 必然失败；修复后真机 integration 可正常执行。
4. **e2e 套件隔离缺陷**：投递序号硬编码（序号漂移即回执被拒）、账号级计数断言（共享 fixture 账号下必然失败）；已抽 `waitForDeliverySeq` 并改为按对象精确断言。
