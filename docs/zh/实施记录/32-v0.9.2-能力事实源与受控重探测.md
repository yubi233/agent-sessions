## 1. 问题（P0 实测钉死的四层归因）

云端拓扑下 Android 真机进入 DSH 会话后，手机显示 **"Provider 当前不可用。"**、发送被禁用。P0 阶段把故障链拆成四层并逐层取证（复现矩阵 10/10 passed，报告 `e2e-verify/reports/2026-09-16T04-36-52-300Z/V092-ATTRIB/`）：

| 层 | 结论 | 性质 |
| --- | --- | --- |
| L1 能力事实源 | 移动端的 Provider 可用性来自 **Relay 进程内嵌 DSH Adapter 的 Detect**；云端 Relay 镜像是 scratch 单二进制（无 node、无 DSH 检出），该探测必然 fail-closed。同一份 `dsh.Adapter` 代码在执行侧 Daemon 进程正常（真实桥 `version=0.0.1`、`model_groups=1`）。 | 产品缺陷 |
| L2 会话生命周期 | store 映射与内存句柄分离；重启后"有映射无句柄"时 send fail-closed（可见失败链已成立），但移动端发送前自动恢复走 `start`（新建实例）而非 `resume`（保留原实例）。 | 产品缺陷（P2 修复） |
| L3 探测缓存死锁 | 首次 Detect 结果被永久缓存：环境修复后同一进程内仍不可用，只能重启进程。 | 产品缺陷 |
| L4 验收口径 | ACC-04/06 的 DSH 旅程由 Daemon 命令调度完成，不经过手机 composer 的能力门控。 | 文档口径（P4 修复） |

**T2 裁决（2026-09-16，基于 P0 实测）**：采用"候选 B 精确化形态"——Relay 按执行侧上报表述派生 DSH 能力，Relay 自身探测仅在其**能真实执行**该 Provider 时作为事实源。不变项：不把凭据放上云、不在云端再装一份 DSH、不新增会话自动创建逻辑、版本门与 fail-closed 语义不回退。

## 2. 本轮交付（P1）

### 2.1 执行侧 Provider 事实源（L1 / G1 / V092-03、V092-04）

**协议（additive，可缺省）**

- `packages/protocol/schema/openapi.yaml` 新增 `ProviderFact` / `ProviderModelGroupFact` / `ProviderModelFact`；`DaemonHelloRequest` 与 `DaemonHeartbeatRequest` 增加可选 `provider_facts`。生成物（Go/TS）由 `tools/generate_protocol.sh` 重生成，未手工编辑。
- 字段只承载安全元数据：`kind`、`available`、`version`、`reason`（执行侧中文原因）、`default_model`、`observed_at_unix_ms`、`model_groups`。**不含**路径、凭据、会话正文或 Provider 配置。

**存储**

- `terminals` 增加 additive 列 `provider_facts_json`（迁移列表末尾，`ALTER TABLE ... ADD COLUMN`；默认空串 = 旧 Daemon 未上报）。
- `UpsertDaemonTerminal` 写入、`TouchTerminalPresence` 支持"携带则整体替换 / `nil` 则保持既有快照"，使环境变化后一个心跳周期内即可纠正对外表述。

**Relay 合并（`internal/domain/provider_facts.go`）**

对每个 Provider 独立判定，纯函数、无 IO、可穷举测试：

1. Relay 自身探测成功（Version 非空）→ 采用 Relay 事实，`facts_source="relay"`；
2. Relay 失败/缺失 + **在线** Terminal 上报可用 → 采用执行侧事实与模型目录，`facts_source="terminal"`；
3. 两侧都没有可用事实 → fail-closed，`facts_source="unavailable"`，原因优先取执行侧上报的当前原因；
4. 执行侧声明**不可用**永远不会被 Relay 的结果伪造成可用。

`/v1/capabilities`（`internal/httpapi/handlers.go`）在返回前合并上述事实；读取失败不阻断查询（退回既有语义，避免把存储抖动升级成全局不可用）。

**客户端**

- 新增 `facts_source` additive 字段（`internal/adapterreg`），回答"谁在声明可用"，**不改变可用性语义**。
- Flutter `ProviderCapabilityProfile` 解析 `facts_source`（旧 Relay 缺字段 → 空串，不报错、不影响门控）；composer 在 Provider 不可用时展示执行侧给出的真实原因，而不是笼统的"Provider 当前不可用"。

**Daemon 上报**

- `internal/daemon/provider_facts.go`：`ProviderFactCollector` 缓存执行侧事实并受 TTL（缺省 60s）控制刷新。**心跳路径永不阻塞在探测上**：首次 `Snapshot` 触发后台采集并返回 nil（"尚未观测"绝不被上报成"不可用"）。
- 采集器与 runner **共享同一份 adapters 实例**（`adapterreg.NewWithAdapters`），因此"上报给 Relay 的能力"就是"真正执行命令的能力"，不会出现两份探测各自为政。
- fixture 模式不上报事实：mock adapter 不代表本机真实执行能力。

### 2.2 受控重探测（L3 / C2 / V092-05）

`internal/adapter/dsh/reprobe.go`：

- 触发条件**集中**在 `shouldReprobeLocked`（已探测过 + 结果为失败 + 冷却已过），调用方不感知；
- 冷却缺省 15s（`AGENT_SESSIONS_DSH_REPROBE_COOLDOWN_MS`；`0` = 不缓存失败，仅诊断/测试）；
- 并发由 `a.mu` 串行化，天然 single-flight；
- **成功快照仍然零成本命中**，绝不退化为"每个请求都 spawn 桥"（握手要 spawn 子进程，有真实成本）；
- 重探失败的**新**原因实时覆盖旧原因，用户看到的是当前事实而非历史陈迹。

## 6. P2 交付（2026-09-16，commit 6db9c43）：会话生命周期与恢复语义

### 6.1 发送前自动恢复改走 resume（V092-06/07/08）

P0 实测的 b5 对照分支证明：daemon 重启后 store 里的 instance 映射仍在、内存句柄已释放，移动端看到 stopped 投影；旧实现发送前无条件补 `session.start`，而 daemon 的 start 走 `session/new` **新建** Provider 实例并覆盖映射——会话看似「恢复」了但上下文断链。

修正（T3 裁决）：

1. 移动端 `_ensureSessionRunnableForSend` 先 resume（capability 与 lease 允许时）；仅当错误面明确指向「本机没有实例映射」才回退 start；其余失败（Provider 不可用 / 版本门 / 环境失败）原样浮出，绝不静默改走 start 掩盖故障。
2. 错误标记与 daemon 文案一一对应（`local_state_missing` / 本机实例 / 本机句柄 / 尚未启动 / 请先启动会话 / `session instance`）。
3. daemon `resumeSession` 统一错误归口：resume **自报成功但未交出/没有可用句柄**与「映射不存在」同归 `ErrSessionInstanceMissing`（协议码 `LOCAL_STATE_MISSING`），客户端才能稳定区分「需要重建本机实例」与真实执行失败；具体原因保留在诊断文案中，不进入公共协议正文。
4. fixture 的 resume 推进会话投影为 idle（与真实 daemon 恢复后一致），并删除因此变成死代码的 `_appendSystemNotice` 助手。

回归：`internal/daemon/v092_lifecycle_contract_test.go`（三类失败可区分、并发恢复串行化且保留原 instance、桥异常退出映射不变且失败收口、重复 start 回收句柄）、`apps/mobile/test/session_send_auto_start_test.dart`（resume 优先 / 仅缺失映射才回退 start）。
