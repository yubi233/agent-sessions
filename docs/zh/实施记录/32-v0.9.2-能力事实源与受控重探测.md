## 1. 问题（P0 实测钉死的四层归因）

云端拓扑下 Android 真机进入 DSH 会话后，手机显示 **"Provider 当前不可用。"**、发送被禁用。P0 阶段把故障链拆成四层并逐层取证（复现矩阵 10/10 passed，报告 `e2e-verify/reports/2026-09-16T04-36-52-300Z/V092-ATTRIB/`）：

| 层 | 结论 | 性质 |
| --- | --- | --- |
| L1 能力事实源 | 移动端的 Provider 可用性来自 **Relay 进程内嵌 DSH Adapter 的 Detect**；云端 Relay 镜像是 scratch 单二进制（无 node、无 DSH 检出），该探测必然 fail-closed。同一份 `dsh.Adapter` 代码在执行侧 Daemon 进程正常（真实桥 `version=0.0.1`、`model_groups=1`）。 | 产品缺陷 |
| L2 会话生命周期 | store 映射与内存句柄分离；重启后"有映射无句柄"时 send fail-closed（可见失败链已成立），但移动端发送前自动恢复走 `start`（新建实例）而非 `resume`（保留原实例）。 | 产品缺陷（P2 修复） |
| L3 探测缓存死锁 | 首次 Detect 结果被永久缓存：环境修复后同一进程内仍不可用，只能重启进程。 | 产品缺陷 |
| L4 验收口径 | ACC-04/06 的 DSH 旅程由 Daemon 命令调度完成，不经过手机 composer 的能力门控。 | 文档口径（P4 修复） |

**T2 裁决（2026-09-16，基于 P0 实测）**：采用"候选 B 精确化形态"——Relay 按执行侧上报表述派生 DSH 能力，Relay 自身探测仅在其**能真实执行**该 Provider 时作为事实源。不变项：不把凭据放上云、不在云端再装一份 DSH、不新增会话自动创建逻辑、版本门与 fail-closed 语义不回退。

## 2. 本轮交付（P1）

### 2.1 执行侧 Provider 事实源（L1 / G1 / V092-03、V092-04）

**协议（additive，可缺省）**

- `packages/protocol/schema/openapi.yaml` 新增 `ProviderFact` / `ProviderModelGroupFact` / `ProviderModelFact`；`DaemonHelloRequest` 与 `DaemonHeartbeatRequest` 增加可选 `provider_facts`。生成物（Go/TS）由 `tools/generate_protocol.sh` 重生成，未手工编辑。
- 字段只承载安全元数据：`kind`、`available`、`version`、`reason`（执行侧中文原因）、`default_model`、`observed_at_unix_ms`、`model_groups`。**不含**路径、凭据、会话正文或 Provider 配置。

**存储**

- `terminals` 增加 additive 列 `provider_facts_json`（迁移列表末尾，`ALTER TABLE ... ADD COLUMN`；默认空串 = 旧 Daemon 未上报）。
- `UpsertDaemonTerminal` 写入、`TouchTerminalPresence` 支持"携带则整体替换 / `nil` 则保持既有快照"，使环境变化后一个心跳周期内即可纠正对外表述。

**Relay 合并（`internal/domain/provider_facts.go`）**

对每个 Provider 独立判定，纯函数、无 IO、可穷举测试：

1. Relay 自身探测成功（Version 非空）→ 采用 Relay 事实，`facts_source="relay"`；
2. Relay 失败/缺失 + **在线** Terminal 上报可用 → 采用执行侧事实与模型目录，`facts_source="terminal"`；
3. 两侧都没有可用事实 → fail-closed，`facts_source="unavailable"`，原因优先取执行侧上报的当前原因；
4. 执行侧声明**不可用**永远不会被 Relay 的结果伪造成可用。

`/v1/capabilities`（`internal/httpapi/handlers.go`）在返回前合并上述事实；读取失败不阻断查询（退回既有语义，避免把存储抖动升级成全局不可用）。

**客户端**

- 新增 `facts_source` additive 字段（`internal/adapterreg`），回答"谁在声明可用"，**不改变可用性语义**。
- Flutter `ProviderCapabilityProfile` 解析 `facts_source`（旧 Relay 缺字段 → 空串，不报错、不影响门控）；composer 在 Provider 不可用时展示执行侧给出的真实原因，而不是笼统的"Provider 当前不可用"。

**Daemon 上报**

- `internal/daemon/provider_facts.go`：`ProviderFactCollector` 缓存执行侧事实并受 TTL（缺省 60s）控制刷新。**心跳路径永不阻塞在探测上**：首次 `Snapshot` 触发后台采集并返回 nil（"尚未观测"绝不被上报成"不可用"）。
- 采集器与 runner **共享同一份 adapters 实例**（`adapterreg.NewWithAdapters`），因此"上报给 Relay 的能力"就是"真正执行命令的能力"，不会出现两份探测各自为政。
- fixture 模式不上报事实：mock adapter 不代表本机真实执行能力。

### 2.2 受控重探测（L3 / C2 / V092-05）

`internal/adapter/dsh/reprobe.go`：

- 触发条件**集中**在 `shouldReprobeLocked`（已探测过 + 结果为失败 + 冷却已过），调用方不感知；
- 冷却缺省 15s（`AGENT_SESSIONS_DSH_REPROBE_COOLDOWN_MS`；`0` = 不缓存失败，仅诊断/测试）；

- **成功快照仍然零成本命中**，绝不退化为"每个请求都 spawn 桥"（握手要 spawn 子进程，有真实成本）；
- 重探失败的**新**原因实时覆盖旧原因，用户看到的是当前事实而非历史陈迹。

## 6. P2 交付（2026-09-16，commit 6db9c43）：会话生命周期与恢复语义

### 6.1 发送前自动恢复改走 resume（V092-06/07/08）

P0 实测的 b5 对照分支证明：daemon 重启后 store 里的 instance 映射仍在、内存句柄已释放，移动端看到 stopped 投影；旧实现发送前无条件补 `session.start`，而 daemon 的 start 走 `session/new` **新建** Provider 实例并覆盖映射——会话看似「恢复」了但上下文断链。

修正（T3 裁决）：

1. 移动端 `_ensureSessionRunnableForSend` 先 resume（capability 与 lease 允许时）；仅当错误面明确指向「本机没有实例映射」才回退 start；其余失败（Provider 不可用 / 版本门 / 环境失败）原样浮出，绝不静默改走 start 掩盖故障。
2. 错误标记与 daemon 文案一一对应（`local_state_missing` / 本机实例 / 本机句柄 / 尚未启动 / 请先启动会话 / `session instance`）。
3. daemon `resumeSession` 统一错误归口：resume **自报成功但未交出/没有可用句柄**与「映射不存在」同归 `ErrSessionInstanceMissing`（协议码 `LOCAL_STATE_MISSING`），客户端才能稳定区分「需要重建本机实例」与真实执行失败；具体原因保留在诊断文案中，不进入公共协议正文。
4. fixture 的 resume 推进会话投影为 idle（与真实 daemon 恢复后一致），并删除因此变成死代码的 `_appendSystemNotice` 助手。

回归：`internal/daemon/v092_lifecycle_contract_test.go`（三类失败可区分、并发恢复串行化且保留原 instance、桥异常退出映射不变且失败收口、重复 start 回收句柄）、`apps/mobile/test/session_send_auto_start_test.dart`（resume 优先 / 仅缺失映射才回退 start）。

## 9. R3 交付（2026-09-16）：Relay→Daemon 命令投递契约修复（真机实测暴露）

### 9.1 缺陷（两处同源契约错位，影响所有非 send 会话命令）

在本地 Relay + 本地 Daemon + 真机拓扑下做 V092-09 验证时，手机点击发送后应用提示「会话恢复未成功，请先手动恢复会话再发送」，而 Daemon 侧日志显示：

```text
kind=session.model_select error="session.model_select 缺少 session_id"
kind=session.resume      error="session.resume 缺少 session_id"
```

逐层定位到两处错位，**都在 Daemon 侧**：

1. **顶层字段丢失**：Relay 的 SSE 把 `session_id` / `workspace_id` 作为 command 的顶层字段下发，而 `RelayCommand→Command` 转换时这些字段没有进入 `Command` 结构（该结构根本没有 `SessionID` 字段），runner 又只从 payload 顶层读 `session_id` —— 于是除 `session.send`（客户端把 session_id 放进了 `fixture_payload`）以外的全部会话命令都以「缺少 session_id」失败。
2. **envelope 层缺失**：Relay 下发的 `ciphertext` 是命令的**子对象**（`{"fixture_payload":{...}}`），而 `parseEnvelope` 期望完整 envelope（`ciphertext.fixture_payload`）—— 即使 session_id 到位，`model` / `effort` 等 fixture 载荷字段仍然读不到。

用户在真机上看到的现象因此是：链路完全可用（第一次发送时桥的原始错误能出现在手机时间线），但**会话恢复/模型切换这类命令全部失败**，发送被前置恢复拦住。

### 9.2 修复（在 Daemon 侧收口，不改 Relay 下行契约）

- `internal/daemon/store.go`： `Command` 增加 `SessionID` 字段（Relay 顶层会话归属），并写明缺陷背景；
- `internal/daemon/relay.go`：投递时把 `command.SessionID` 一起交给 runner；`commandPayloadJSON` 补 envelope 层（已有 `ciphertext` 键的输入原样使用，幂等），并继续注入顶层 `session_id`/`workspace_id`（不覆盖已有值）；
- `internal/daemon/runner.go`：新增 `sessionIDFrom(cmd, env)`，payload 优先、缺失时回退到命令顶层字段；14 处命令分支统一改用它。

### 9.3 验证

- 新增回归 `internal/daemon/v092_command_payload_test.go`（payload 必须能被 runner 解析出 session_id 与 model、既有 envelope 幂等不重复包裹、空/非 JSON 原样透传）与 `internal/daemon/v092_session_id_fallback_test.go`（payload 缺失时回退顶层、payload 优先、双侧皆无返回空串）。

## 10. R5 交付（2026-09-16）：T7 state-dir 单实例锁（从「已实证」到「已实现」）

### 10.1 裁决（计划 §7 T7 由待裁决转为已裁决并实现）

**裁决：实现 state-dir 单实例锁，多实例一律 fail-loud 拒绝启动。** 依据是 R4 的可复现实测：同一 state-dir 上并存 3 个 Daemon（`go run` 包装 + 多个编译产物子进程）时，它们共享同一份 Relay 终端身份与 delivery_seq 游标，命令被多个消费者竞争并以 `DAEMON_EXECUTION_FAILED` 收场；清理为单实例后**同样的命令一次通过**（delivery=26 `succeeded`）。

### 10.2 实现

| 文件 | 内容 |
| --- | --- |
| `internal/daemon/statedir_lock.go` | 锁原语：state-dir 规范路径哈希 → 系统临时目录下的 lock 文件；fail-loud 错误（含 state-dir 与持有者 pid）；诊断开关 `AGENT_SESSIONS_DAEMON_ALLOW_MULTI_INSTANCE=1` |
| `internal/daemon/statedir_lock_unix.go` | Unix flock 非阻塞独占锁实现；加锁成功写入本进程 pid 供后续实例报告 |
| `internal/daemon/statedir_lock_other.go` | 非 Unix 空实现（保持既有行为，不引入未验证平台的新失败模式） |
| `apps/daemon/main.go` | `cmdRun` 启动即加锁，defer 释放 |

设计要点：

1. **锁随描述符释放**：flock 的锁绑定在打开的文件描述符上，进程退出（含被 kill）由内核自动释放——**不留需要人工清理的陈旧锁**；锁文件本身不删除（删除会让并发启动各自创建新 inode，失去互斥意义）。
2. **锁文件放系统临时目录**而非 state-dir 内部：避免「删目录重建」流程里出现「锁文件还在、目录已新」的歧义。
3. **fail-loud 而非静默降级**：拒绝信息同时给出锁路径、state-dir 与持有者 pid，用户与回归脚本可直接定位。

### 10.3 验证

- 单元/契约回归 `internal/daemon/v092_statedir_lock_test.go`（5 例，全绿）：拒绝第二持有者、释放后可重获、不同目录互不影响、诊断开关可绕过、锁路径哈希稳定且相对/绝对归一。
- **跨进程真实验证**（单进程测试无法证明 flock 语义，因此必须实测）：

```text
[实例一] daemon relay loop / relay command scheduler started / relay generation recorded
[实例二] daemon: state-dir 已被另一个 Daemon 实例占用:
         /var/folders/.../agent-sessions-daemon-5de1566126175045.lock
         （state_dir=/tmp/v092-locktest，持有者 pid=88918）。
         请先停止已有 Daemon，或用 AGENT_SESSIONS_DAEMON_ALLOW_MULTI_INSTANCE=1 临时绕过（仅诊断）
```

即：单实例正常运行，第二实例启动即被明确拒绝并说明原因与持有者。

### 11.6 因果链闭合（R6，决定性）

## 12. R11 重大转折：链路其实是通的——真因是账户余额与两条目录路径不一致

### 12.1 新证据（决定性）

清空 Daemon 本地 state 并单实例重启后，历史上曾失败的 `session.send` 被重放，日志出现**此前从未见过的错误形态**：

```text

  Internal error: turn failed: 401: {"type":"CreditsError",
```

这条错误说明三件事，**推翻了此前 11 轮的归因结论**：

1. `session/set_config_option` 的模型路由**被桥接受了**（否则不会走到 prompt）；
2. `session/prompt` **真的调用了真实模型服务**（opencode.ai）；
3. 失败原因是**账户余额不足**（`CreditsError / Insufficient balance`）——属用户侧计费状态，不是代码缺陷。

### 12.2 归因修正（为什么前几轮的结论是错的）

此前把`"所有路由都被拒"` 当作不可动摇的事实，据此推断`"桥内部 catalog 与路由校验不同源"`。实际是**两条独立的目录路径被混为一谈**：

| 路径 | 数据来源 | provider 表现 |
| --- | --- | --- |
| **能力/事实路径**（`GET /v1/capabilities` 的模型目录） | Daemon 的 ProviderFact 采集器（`Detect` 探测桥）→ 上报 Relay → 合并 | 显示 `deepseek-official` + `deepseek-v4-*` |
| **会话执行路径**（真实发送用的目录） | 跨会话 `initialize` 握手带回（`storeHandshakeLocked`） | 用本仓库传入的 `cordis.yml`（provider 为 `goat/opencode-go/opencode-zen/…`） |

独立验证：直接用 `node bin.js -c <agent-sessions/cordis.yml>` 起桥并做 initialize/session/new/set_config_option，桥公布的是 `goat` 等 provider，模型值为 **URL 编码**形态（如 `dsh:model:goat:deepseek%2Fdeepseek-v4-flash`）；而 `capabilities` 里那三条 `deepseek-official` 条目**不带编码**——两者不是同一份目录，前者的 provider 名与 DSH 默认配置 `examples/acp-agent/cordis.yml`（`provider: deepseek-official / model: deepseek-v4-pro`）完全一致。

**因此**：手机侧依据 `capabilities` 那条目录选择模型 → 回传的路由在**会话执行路径**的目录里不存在 → `-32602；而当路由恰好命中执行路径目录时（如 `goat` 那条），发送会一路走到真实模型，然后因**余额不足**失败。

### 12.3 真正的缺陷与修复方向（本仓库侧，首次明确）

**缺陷**：同一个 Provider 的模型目录在本仓库内存在**两个来源**且未对齐——能力事实路径（`Detect` 探测所用配置）与会话执行路径（`Start/Resume` 握手所用配置）取到的目录不同。用户在能力页/模型选择器里看到的模型，未必是发送时真正可用的模型。这**正是 v0.9.2 P1`"能力事实源"` 要解决的问题的延伸**：事实源必须与实际执行路径一致。

**证据链**：

- 探测桥目录 provider = `deepseek-official`（同 DSH 默认配置）；
- 会话桥目录 provider = `goat` 等（同本仓库 cordis.yml）；
- 两者都经由 `binConfig()` 解析配置（已用单测确认环境变量生效），差异出现在**桥被启动时的实际入参或环境**，需要继续定位到具体分支。

**下一步（下一轮直接可做）**：

1. 在 `Detect` 与 `Start` 两条桥启动路径上分别打印实际命令行（`bin/-c/config/cwd`）与 initialize 返回的目录 provider 集合，定位分叉点；
2. 修复后使两条路径共用同一份目录（优先：让能力上报读取会话执行路径的目录，或让两者共用同一 `adapter` 握手缓存）；

**验证二：采集器与执行器同实例**。apps/daemon/main.go 中 loop.ProviderFacts = daemon.NewProviderFactCollector(adapterreg.NewWithAdapters(adapters))，与 runner 共用同一个 adapters map（代码注释明确写着「不会出现两份探测各自为政」）。所以**不是两个 adapter 实例各探各的**。

**因此分叉只可能落在 Relay 侧保留的终端 facts 快照**：Daemon 心跳只在 providerFacts != nil 时上报，**第一次成功探测之前不上报**；而上一轮换配置/清 state 时，Relay 只能保留旧快照。capabilities 读的正是该快照（OnlineTerminalFacts → MergeProviderFacts），因此它可能仍是**旧配置时期**采集到的 deepseek-official 目录。

**下一轮的直接验证（一条命令级操作）**：清空 Relay 的终端 facts（或让 Daemon 在全新账号下重新配对并完成首次探测），再读 GET /v1/capabilities——若目录变为 goat/opencode-*，则「两条目录不一致」确认由**陈旧快照**造成，属可修复的**事实新鲜度**问题（可加「facts 与当前 adapter 配置版本不一致则视为过期」的判定）。

### 12.6 用户观察（本轮）与结论修正

用户指出：「dsh 应该不需要用到 key 才对」、「这个配置有问题吧 provider: deepseek-official / model: deepseek-v4-pro」。前者与本轮实测一致——DSH 的凭据平面是 ~/.dsh/.credentials.yaml（内含 OPENAI/XIAOMI_TOKEN_PLAN_CN/GOAT/AXIS_GROK 等键）+ DSH 检出根 .env，由桥自身加载，**本仓库不读取不转储**（minimalEnv 只传 PATH/HOME/TMPDIR/DSH_SNAPSHOT*）。后者指向的 provider: deepseek-official / model: deepseek-v4-pro 经核对**不在** agent-sessions/cordis.yml，而正是 DSH 仓库默认样例 examples/acp-agent/cordis.yml 的内容——它出现在 capabilities 里，正是「陈旧快照/来源未对齐」的直接症状。

### 12.7 R11 最终实验：桥实际公布 7 组 provider，客户端只看到 1 组

用探针复刻 adapter 的启动条件（完整环境 / minimalEnv / cwd=/tmp / cwd=DSH 检出根 四种组合），**结果完全一致**：

```text
providers: [deepseek-official, opencode-go, opencode-zen, openai, xiaomi-token-plan-cn, goat, axis-grok]
current:   dsh:model:opencode-zen:nemotron-3-ultra-free
```

三点结论：

1. **环境与 cwd 不是分叉原因**（四种组合同一结果）——此前「环境导致回退」的怀疑排除；
2. 传 `-c agent-sessions/cordis.yml` 时桥公布的 current 是 `opencode-zen:nemotron-3-ultra-free`，**与 cordis.yml 的 acp-agent.provider/model 完全一致**，说明配置确实生效；
3. **客户端只看到 1 组（deepseek-official + deepseek-v4-flash/pro），而桥公布 7 组**——差异出现在**本仓库到 Relay 的上报/合并链路**，属本仓库可修范围：

```text
桥 initialize _meta → adapter storeHandshakeLocked(a.modelGroups = 全部 7 组)
                    → registry/daemonCapabilities → ProviderFactPayload
                    → Relay MergeProviderFacts → GET /v1/capabilities（只看到 1 组）
```

**下一轮定位起点（已很窄）**：核对 `internal/daemon/provider_facts.go` 的 `providerFactFromRegistry` 与 `internal/httpapi/daemon.go` 的上报结构之间 `model_groups` 的组装——重点看是否只上报 current 所属组，或被 `maxProviderFactGroups` 之类上限截断。

### 12.8 对用户两个判断的回应

- **「dsh 应该不需要用到 key」**：正确。DSH 凭据平面是 `~/.dsh/.credentials.yaml`（键含 OPENAI / XIAOMI_TOKEN_PLAN_CN / GOAT / AXIS_GROK）+ DSH 检出根 `.env`（含 OPENCODE_GO / OPENAI / ZAI_CODING_CN），由桥自身加载；本仓库 `minimalEnv` 只传 PATH/HOME/TMPDIR/DSH_SNAPSHOT* 并 scrub 其他凭据变量，**不读取不转储**。
- **「provider: deepseek-official / model: deepseek-v4-pro 这个配置有问题」**：正确，且正是症状所在。该组合不在 `agent-sessions/cordis.yml` 的 `acp-agent` 段（那里是 `provider: opencode-zen` / `model: nemotron-3-ultra-free`，与桥实测 current 一致）；它出现在 capabilities 里，说明**上报链路上有一处把模型目录替换/裁剪成了另一份内容**——这正是下一步要修的本仓库缺陷。

## 13. R12 根因确认与修复：本地 Relay 未传 DSH 配置导致目录被顶替

### 13.1 完整因果链（12 轮排查的终点）

```text
① 本地 Relay 启动命令：.task/restart/relay --addr 127.0.0.1:8787 --db …
   —— **未设置 AGENT_SESSIONS_DSH_CONFIG**（实测 ps eww 无该变量）
② Relay 自带 DSH adapter，探测时用适配器缺省配置：
   /Users/yubi/code/deepseek-harness/examples/acp-agent/cordis.yml
   该文件内容正是 provider: deepseek-official / model: deepseek-v4-pro
③ handleCapabilities 的 T2 语义：Relay 自己探测成功 → **以自己为准**，
   不采用执行侧（Daemon）上报的 facts（实测 facts_source=relay）
④ 于是客户端在 /v1/capabilities 看到 deepseek-official + deepseek-v4-flash/pro/vision-exp
   —— 与 Relay 缺省配置一字不差，也与 Daemon 实际执行目录（6 组）无关
⑤ 手机按该目录选模型 → 回传 dsh:model:deepseek-official:<model> →
   在 Daemon/桥的真实目录里不存在 → -32602 unknown model route
```

### 13.2 修复与验证

让 Relay 与 Daemon 共用同一份 DSH 配置：

```bash
AGENT_SESSIONS_DSH_CONFIG=/…/agent-sessions/cordis.yml \
  .task/restart/relay --addr 127.0.0.1:8787 --db .task/restart/relay.db
```

重启后 `GET /v1/capabilities` 立即返回正确目录：

```text
available: true   default: dsh:model:opencode-zen:nemotron-3-ultra-free
group opencode-go(1)  opencode-zen(4)  openai(3)  xiaomi-token-plan-cn(2)  goat(5)  axis-grok(1)
```

`deepseek-official` 与未编码模型名全部消失，且 default 与 cordis.yml 的 `acp-agent.provider/model` 一致。

交叉验证（同一轮）：`internal/adapter/dsh` 侧 live 测试直接打印 adapter 收到的目录为 **6 组**、default 为 `opencode-zen:nemotron-3-ultra-free`——与修复后的 capabilities 完全一致，证明**本仓库解析层没有问题**，问题只在 Relay 进程的启动环境。

### 13.3 工程结论（需要写进运维约定）

1. **本地/自建 Relay 与本机 Daemon 必须使用同一份 `cordis.yml`**。T2 裁决规定 Relay 自身探测成功时以其为准；当 Relay 与 Daemon 配置不同（或 Relay 没配而 Daemon 配了）时，客户端看到的模型目录来自 **Relay 的配置**，而不是真正执行命令的 Daemon 的配置——这会直接导致"选得到的模型发不出去"。
2. 该现象**只在本机同时跑 Relay 与 Daemon 时出现**；云端拓扑下 Relay 是 scratch 镜像、无 node 与 DSH 检出，探测必然失败，因此按 T2 正确回退到执行侧事实（R2 云端实测的 `available=true/version=0.0.1` 即此路径）。
3. 记录 32 §11.12–§11.20 关于"上游 catalog 缺陷"的结论**全部作废**；真实原因是本机 Relay 的启动环境缺一个环境变量。

### 13.4 对 V092-09/10 的影响

- 目录不一致这一层**已解除**：手机现在能拿到与实际执行一致的模型目录；
- 剩下的唯一障碍是**账户余额**：`goat` 渠道（`api.commandcode.ai` / opencode.ai）返回 `CreditsError`；而正确目录里的 `opencode-zen` 免费池模型（`nemotron-3-ultra-free` 等）**不需要余额**，因此现在具备复跑 V092-09 的完整条件；
- 若手机侧仍缓存旧目录，需重启应用（或强制刷新能力）后在模型选择器中选择 `opencode-zen` 组内的模型再发送。
