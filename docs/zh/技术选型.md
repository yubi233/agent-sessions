# Agent Sessions 技术选型

> 状态：推荐基线，待实现 P0 时锁定版本（2026-08-13）
>
> 本文回答“各技术栈具体用什么”的问题。业务边界见[项目文档](项目文档.md)，阶段依赖见[实施计划](实施计划.md)。

## 1. 先解决语言约束

Flutter 和 TypeScript 不能同时作为同一客户端的实现语言：

- Flutter 的 UI、状态、网络、存储和业务代码使用 Dart。
- Android 原生平台插件使用 Kotlin。
- Vue3 Web/Admin 和 Node 工具链使用 TypeScript。
- 三端通过 OpenAPI/JSON Schema 生成各自的 DTO，不通过共享源码实现跨语言复用。

本项目的推荐选择是保留 Flutter，因此 Android 使用 Dart。只有“所有客户端源码必须是 TypeScript”高于“必须使用 Flutter”时，才改为 React Native；不能把 TypeScript 嵌入 Flutter 当作可行折中。

## 2. 仓库与版本基线

| 范围 | 选择 |
| --- | --- |
| JavaScript 包管理 | pnpm workspace，锁定 `pnpm-lock.yaml` |
| Web 构建 | Vite，不使用 Nuxt/SSR |
| TypeScript | `strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes` |
| Go | Go 1.26.x，根目录单一 `go.mod`，两个二进制入口 |
| Flutter | stable channel，Dart 3.x，单独 `pubspec.yaml` |
| Android 原生 | JDK 21、Kotlin，仅用于平台插件和系统能力 |
| 任务入口 | 根目录 `Taskfile.yml`，CI 与本地复用同一命令 |
| CI | GitHub Actions，静态检查、单元、集成、构建分层执行 |

采用单一 Go module，而不是 Relay/Daemon 各自维护 module：共享协议、加密和错误包可以直接复用，依赖升级和交叉编译更简单。Vue 应用仍保持独立入口，通过 pnpm workspace 共享协议客户端和设计 token。

## 3. Vue3 + TypeScript

### 3.1 基础栈

| 能力 | 推荐选型 | 说明 |
| --- | --- | --- |
| UI 框架 | Vue 3 + Composition API | 两个 Web 应用统一模型 |
| UI 组件库 | Element Plus | 管理台的表格、树、表单、抽屉、弹窗和状态控件成熟；Web 会话端只复用基础控件 |
| 图标 | `lucide-vue-next` | 不使用组件库默认图标作为产品图标 |
| 路由 | Vue Router | Admin/Web 分别维护路由和权限边界 |
| 客户端状态 | Pinia | 只存认证、连接、UI 偏好和本地编辑状态 |
| 服务端状态 | `@tanstack/vue-query` | 查询缓存、失效、重试和分页不复制到 Pinia |
| REST | OpenAPI 生成类型 + `openapi-fetch` | 禁止手写重复 DTO |
| SSE | `@microsoft/fetch-event-source` | 支持 abort、重连和 `Last-Event-ID` |
| WebSocket | 浏览器原生 WebSocket | 自己实现协议 envelope、游标和重连状态机 |
| 本地缓存 | Dexie + IndexedDB | 只缓存密文、游标和非敏感索引 |
| 虚拟列表 | `@tanstack/vue-virtual` | 会话长列表和 Diff 行渲染 |
| Markdown | `markdown-it` + DOMPurify | 只允许白名单标签，禁止直接渲染不可信 HTML |
| 代码高亮 | `highlight.js` | 按常用语言拆分加载 |
| PWA | `vite-plugin-pwa` | 仅 Web App 使用；Service Worker 不缓存解密后的正文 |

### 3.2 UI 框架边界

应该使用 UI 框架，但不要把所有产品界面都套成后台表格：

- Admin 使用 Element Plus 作为主组件库。
- Web 会话端使用 Element Plus 的按钮、菜单、Tabs、Dialog、Tree 等基础控件，并用项目自己的 design token 覆盖主题。
- 聊天时间线、工具调用卡、权限卡、Plan/Goal 面板、Skill 表单和 unified/split DiffView 都是领域组件，自行实现。
- 不同时引入 Vuetify、Naive UI、Ant Design Vue 或 Tailwind 组件套件，避免主题、交互和无障碍语义分裂。
- 不使用 Monaco 作为首版 DiffView；协议直接返回结构化文件、hunk、line，前端用虚拟列表渲染，包体和 Worker 更可控。

### 3.3 质量工具

- `vue-tsc`：Vue SFC 类型检查。
- ESLint 9 + `eslint-plugin-vue` + `typescript-eslint`。
- Prettier：只做格式化，不承担业务 lint。
- Vitest：单元和 composable。
- Vue Testing Library：组件行为和可访问性语义。
- MSW：REST/SSE/Provider fixture；不在组件测试中请求真实服务。
- Playwright：Admin/Web 的 headed E2E 和 CI headless 回归。

## 4. Flutter Android + Dart

### 4.1 基础栈

| 能力 | 推荐选型 | 说明 |
| --- | --- | --- |
| UI | Flutter Material 3 + 自有 Design System | 不引入大而全的第三方组件套件 |
| 状态/依赖注入 | Riverpod `Notifier`/`AsyncNotifier` | 可测试、支持异步状态和生命周期；不使用 GetX |
| 导航 | `go_router` | 深链、登录守卫和会话路由 |
| REST | Dio | 拦截器、超时、取消和统一错误映射 |
| WebSocket | `web_socket_channel` | 协议帧由领域层解析，不把 socket 状态散落在页面 |
| SSE | 基于 Dio stream 的小型 SSE decoder | 复用统一 cursor/reconnect 状态机 |
| DTO | Freezed + `json_serializable` | wire DTO 与领域模型分离 |
| 本地数据库 | Drift | 保存密文 envelope、游标和最小索引；不保存解密正文 |
| 安全存储 | `flutter_secure_storage` + Android Keystore | 保存设备私钥包装密钥和 refresh token |
| 密码学 | `cryptography` + `cryptography_flutter` | 不自行实现 AES-GCM、HKDF、X25519、Ed25519 |
| Markdown | `flutter_markdown` | 事件文本先经过事件类型和链接白名单校验 |
| 语法高亮 | `highlight` | Diff 行使用自有渲染模型 |
| QR | `mobile_scanner` | 配对二维码扫描 |
| 附件 | `file_picker`、`image_picker` | 只允许计划中的图片和文本 MIME |
| 通知 | `flutter_local_notifications` | 前台和本地降级通知 |
| 推送 | 仓库内 Kotlin UnifiedPush 插件 | 核心能力不绑定维护状态不明的 Dart 插件 |

### 4.2 Flutter UI 边界

- Material 3 只提供基础交互和平台适配。
- 会话时间线、权限请求、问题表单、Plan/Goal、Skill 参数、DiffView 是项目自有组件。
- DiffView 使用 `CustomScrollView`/`SliverList`，窄屏默认 unified，宽屏可切换 split。
- 不把 Monaco 或网页 DiffView 嵌入 WebView，避免滚动、字体、无障碍和内存问题。
- Drift 中的业务正文必须是密文；解密后的文本只存在于内存状态。

### 4.3 Flutter 质量工具

- `flutter_test`：单元和 widget 测试。
- `integration_test`：Android 模拟器/真机流程。
- Mocktail：Repository、WebSocket、推送和 Provider fake。
- `very_good_analysis`：严格静态检查；允许在项目级 lint 配置中加少量例外。
- `dart format`、`dart analyze` 和 `flutter build apk --debug` 纳入 CI。

## 5. Go Relay Server

### 5.1 基础栈

| 能力 | 推荐选型 | 不选的方案 |
| --- | --- | --- |
| HTTP 路由 | `github.com/gin-gonic/gin`（基于标准 `net/http`） | Fiber；Gin 生态成熟，路由、参数绑定、统一错误响应和中间件足够覆盖首版 |
| Gin 中间件 | `gin-contrib/cors`（只在需要跨域的部署启用）+ 项目自有鉴权、request-id、限流和审计中间件 | 不把业务规则放进第三方全局中间件；CORS 默认关闭或使用显式白名单 |
| WebSocket | `github.com/coder/websocket` | 不新增 Socket.IO；协议是自有 JSON envelope |
| SSE | 标准库 `http.Flusher` | 不引入独立 SSE server 框架 |
| PostgreSQL | `pgx/v5` + `pgxpool` | database/sql 适配层和 GORM |
| SQL | sqlc | 显式 SQL、编译期类型；不使用 GORM 自动迁移 |
| 迁移 | Goose | 迁移文件纳入 Git，部署前显式执行 |
| Redis | `github.com/redis/go-redis/v9` | Redis 不保存会话真相 |
| 配置 | `caarlos0/env/v11` + 内部 typed config | 不使用 Viper 的隐式多来源合并 |
| 日志 | `log/slog` JSON handler | 强制字段白名单和密文脱敏；不输出正文 |
| 观测 | OpenTelemetry + Prometheus client | 首版不引入 Kafka/NATS/Temporal |
| 密码哈希 | Argon2id（`golang.org/x/crypto`） | 不使用 bcrypt 作为新账号默认 |
| Token | 短期 opaque access token + 轮换 refresh token | 首版不使用 JWT，便于撤销、单租户部署和审计 |
| ID | UUIDv7 | 事件顺序以数据库序号为准，ID 不承担排序唯一职责 |

### 5.2 Relay 内部边界

```text
internal/
  auth/          密码、设备 challenge、token、owner
  httpapi/       REST handler、middleware、error mapping
  ws/            controller/terminal WebSocket
  sse/           cursor、Last-Event-ID、flush/backpressure
  domain/        Session、Command、Lease、Capability 规则
  store/pg/      sqlc queries、transaction、outbox
  store/redis/   presence、短 lease、限流、fanout
  router/        authenticated scope 与 typed RPC routing
  observability/ slog、OTel、metrics、health
```

Gin handler 只负责请求绑定、鉴权上下文读取、调用 use-case 和响应映射；业务规则放在 `domain`/`application`，不能把 `*gin.Context` 传入领域层。数据库事务、outbox 和命令幂等必须在 service/use-case 层完成，不能由 HTTP handler 自己拼 SQL。

Gin 只覆盖 REST、健康检查和内部 HTTP 管理接口。SSE 在 Gin handler 中通过 `c.Stream`/`http.ResponseWriter` 完成显式 flush、心跳、cursor 和背压；WebSocket 仍由 `coder/websocket` 完成升级和连接生命周期，Gin 只负责鉴权和路由入口。这样保留 Gin 的工程效率，同时让长连接协议的恢复语义可测试、可审查。

### 5.3 Relay 测试工具

- `go test`、`httptest`、`go test -race` 和 Go fuzzing。
- Testcontainers-Go：需要真实 PostgreSQL/Redis 时使用隔离容器。
- Testify `require`：只作为断言库，不隐藏标准测试生命周期。
- golangci-lint、govulncheck。

## 6. Go PC Daemon

| 能力 | 推荐选型 | 说明 |
| --- | --- | --- |
| CLI | Cobra | `login`、`pair`、`project`、`session`、`doctor` 等命令 |
| 配置 | `pelletier/go-toml/v2` | Daemon 使用 TOML；密钥不写配置文件 |
| SQLite | `modernc.org/sqlite` | 纯 Go、避免 CGO，方便 Windows/macOS/Linux 交叉编译 |
| 系统凭据 | `zalando/go-keyring` | 接入 macOS Keychain、Windows Credential Manager、Linux Secret Service |
| 后台服务 | `kardianos/service` | 统一系统服务安装、启动、停止和卸载 |
| 重连 | `cenkalti/backoff/v5` | 有上限的指数退避和 jitter |
| 并发/退出 | 标准库 context + `errgroup` | 统一取消、进程树退出和资源回收 |
| 文件提示 | fsnotify | 只用于提示刷新，不绕过 Workspace 安全校验 |
| Provider 进程 | `os/exec` + context | 参数数组调用，不经过 shell |
| Git | 系统 Git + porcelain v2 `-z` | 对 submodule、LFS、attributes 和真实工作区行为兼容 |

不选 go-git 作为默认 Git 实现：它不能完全复现用户系统 Git、LFS、配置和 hook 行为。Git 解析器必须有特殊文件名、rename、binary、submodule、untracked 和超大输出测试。

Daemon 如果提供本机诊断或管理 HTTP 接口，也复用 Gin；会话控制仍只通过 Relay WebSocket，不额外开放任意远程 HTTP 命令接口。

Provider 客户端优先使用标准库：Claude stream-json、Codex stdio JSON-RPC、OpenCode HTTP/SSE、OpenClaw WebSocket。暂不引入通用 Agent SDK 或重量级 JSON-RPC 框架；只有实际协议需要时，才在对应 adapter 内增加依赖。

## 7. 协议、代码生成与密码学

### 7.1 协议

- REST 以 OpenAPI 3.1 为事实源。
- WebSocket/SSE envelope 和业务事件以 JSON Schema Draft 2020-12 为事实源。
- Go REST 边界使用 `oapi-codegen` 的 Gin server 模式生成请求/响应 DTO 和接口骨架；业务领域模型不直接使用生成类型。生成的 server interface 由 `httpapi` adapter 实现，避免 OpenAPI 生成器反向决定领域结构。
- TypeScript REST 客户端使用 `openapi-typescript` + `openapi-fetch`。
- Dart REST 边界使用 OpenAPI Generator 生成 DTO/API 层，再映射到 Freezed 领域模型。
- 事件 DTO 使用 schema 生成或校验；生成文件禁止手改，CI 检查 schema、生成物和 golden vectors。

### 7.2 密码学

- Go：标准库 `crypto/ed25519`、`crypto/ecdh`、AES-GCM、HKDF-SHA256。
- TypeScript：WebCrypto 负责 AES-GCM/HKDF，`@noble/curves` 负责 Ed25519/X25519。
- Dart：`cryptography`/`cryptography_flutter`。
- 所有端共享固定的加密、篡改、AAD 和密钥包装测试向量。
- envelope 固定包含算法版本、key id、96-bit nonce、ciphertext、AAD hash 和 payload version。

## 8. 部署与发布

- Docker Compose：Relay、PostgreSQL 16、Redis 7、Caddy。
- Caddy 负责 TLS、静态文件和 `/v1` 反向代理；Relay 不自行处理证书续期。
- PostgreSQL 迁移使用 Goose；备份使用 `pg_dump`/恢复演练。
- GoReleaser 负责跨平台二进制和校验文件；deb/rpm 使用 nfpm，Windows MSI/macOS pkg 使用独立签名流水线。
- GitHub Actions 分开执行 Go、Node/Vue、Flutter 和容器检查。

## 9. 明确不引入的技术

- 不使用 Fiber/GORM/Viper；HTTP 服务统一使用 Gin 生态。
- 不在 Gin handler 中写 SQL、执行业务编排或持有长生命周期会话状态。
- 不使用 Socket.IO、Kafka、NATS、Temporal、Kubernetes 作为首版依赖。
- 不同时使用多个 Vue UI 组件库。
- 不在 Flutter 中引入 GetX 或网页 Monaco。
- 不把 Tailwind 当作组件框架；如后续需要原子 CSS，只能作为内部样式工具，不能替代交互组件。
- 不把 JWT、服务器明文搜索或任意远程 shell 作为默认能力。

## 10. 仍需在 P0 锁定的内容

以下不是架构方向悬而未决，而是初始化时必须锁定的具体版本：

- Go、Node、pnpm、Flutter、JDK 的精确 patch 版本。
- Gin、Element Plus、Riverpod、Dio、Drift、`coder/websocket` 等依赖的 lockfile 版本。
- OpenAPI/JSON Schema 代码生成器版本和生成命令。
- Android UnifiedPush distributor 的部署方式。
- 真实 Provider 的最低支持版本和 live gate 凭据策略。
